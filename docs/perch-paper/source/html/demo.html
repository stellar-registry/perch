1 · Install and spend

Vary whole-XLM amounts and the window. A refusal is displayed from the runtime response, never inferred by the page. Replacing a grant changes installed policy; reset for independent experiments.

2 · Recover with two guardians

The loss profile requires both guardians, a ten-ledger delay and completion within its window. Each successful submitted transaction also advances this simulator's ledger.

3 · Test the recovery boundary

Try grant 1 after recovery before collecting it. Fresh credential installation uses the current owner; spending with grant 2 uses that fresh app credential.

4 · Call the actual game

Both outcomes require guesser authorization. A loss has a game guess root and an outgoing transfer child; two losses fit the cap and a third is refused. A win has only the game root in the guesser’s auth entry; the game pays its own funds. “Run winning fixture” reads the number from local simulator storage without changing it or adding a contract API. Choose missing authorization or a wrong credential to see either branch refused. Inspect the game authorization tree after a call.

    Send a JSON command

    The controls send these same commands to Rust. For example, vary amount_xlm, cap_xlm, period_ledgers or ledgers within the bounds shown above. Malformed supplied values (including null, fractions and empty controls) produce a driver error before acting. Only omitted fields use defaults: amount_xlm 6, cap_xlm 10, period_ledgers 100, ledgers 11, guardian 1, grant_id 1, auth "valid" and owner "current". Grant IDs must fit an unsigned 32-bit integer; owner accepts "current" or "old", and auth accepts "valid", "missing" or "wrong". A typed guess requires number in 0–10.
