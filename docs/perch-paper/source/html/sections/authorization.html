The app signs the transaction's authorization entry with its key and submits the transaction itself or through a relayer. The account then checks the request in a fixed order. A refusal at any step stops it and writes nothing.

  1. Guards refuse calls no grant may ever make, such as a call to the account's adopted recovery contracts.
  2. The account looks up each rule the transaction names, and that rule's spending record.
  3. The decision function, rule_eval::check_auth in the rule-core library {{cite:rule-core}}, checks every call against its rule and computes the new spending records. It reads no storage and checks no signature, and it is the part the proofs cover.
  4. Only if the decision function accepts does a verifier contract check the app's signature.
  5. Only if the signature is valid does the account store the new spending records.

The decision function reports a refusal as contract error {{fact:auth-error-rule-eval-refused}}, or {{fact:auth-error-stale-scope}} for a grant from before a recovery.

The app signs as an external signer: a public key, such as an Ed25519 key or a passkey, whose signatures the account checks through a verifier contract. The transaction names the rule it relies on, and the app's signature covers that choice as well as the call and the account. A relayer that submits the transaction for the app therefore cannot switch it to another rule that lists the same key, such as an uncapped one.

A rule can instead name a delegated signer: another Stellar address that approves through the host rather than with a signature the account checks. In Perch, a delegated signer's approval does not cover the rule choice, so whoever submits the transaction can pick any rule that lists that address. OpenZeppelin {{fact:oz-v080-tag}} covers it for both kinds of signer, at the cost of a separate authorization entry for each delegate. Until Perch closes this gap, an owner should not list one delegated signer in rules of different strength.

A stolen app key meets the same checks

Whoever holds the app's key, whether the app itself or a thief, gets the same checks - the account can't tell them apart. Under the shop grant, that key can send at most {{fact:shop-cap-xlm}} XLM to the shop in any {{fact:shop-period-ledgers}} ledgers and nothing more: it can't use another token, pay anyone else, call another function or change the account. A thief who narrows the grant for a helper gets no more than the grant itself allows.

The owner can stop a stolen key in three ways. Removing the grant with one call, remove_grant, deletes its rules and spending records. Without that, the grant's rules stop working when they expire. If the owner loses their own key, recovering the account advances one counter on it. In that same transaction, every earlier grant stops authorizing, along with every grant narrowed from one. The vision paper covers the owner's key, guardians and the verifier registry.
