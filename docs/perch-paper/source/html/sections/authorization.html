The full authorization path and signature binding

A transaction carries authorization entries, each with a tree of calls. The host gives the account those contexts; the payload selects one rule per context. For ordinary authorization, Perch first applies its account guards, then the evaluator checks eligibility and computes tentative spending records. The shell authenticates the supplied signers and commits records only after success. Recovery completion uses a separate controller path. A failed invocation rolls back. The Lean proof covers the pure evaluator, not all of these surrounding steps. {{cite:cap-0046-11,stellar-custom-account,rule-core}}

An external signer's digest binds the account and selected rule IDs. A delegated signer uses the host's approval path; Perch does not bind rule choice in that delegated path. See the comparison for the pinned OpenZeppelin design's different behavior.

Owner control, recovery, and a stolen app key

The shop grant cannot authorize another recipient, token or function. That is a property of this grant's predicates, not an automatic recipient restriction on every grant. Authority also depends on the other rules installed for the same credential and on the trusted verifier.

The owner calls remove_grant to remove a current-source grant. Completing recovery advances the grant generation; all earlier grants stop authorizing. An ordinary owner edit does not perform that global wipe. The owner, recovery configuration and verifier registry remain trust boundaries. Recovery · Threat model.

A grant covers the calls a request makes

A request is often a call to another contract that then acts with the account's authority. A guessing game's guess takes a stake: on a loss, the game transfers {{fact:nested-stake-xlm}} XLM from the player's account to itself, in a call inside the root call. The account's authorization entry holds that whole tree, and the account checks each call in it against the rule the transaction names for that call. A rule may also name the one root call it serves (docs/auth-root.md). In {{ref:fig:fig-nested}}, the pay-game rule allows the XLM token's transfer only from the account, only to the game, only when the entry's root call is exactly game.guess, and at most {{fact:nested-cap-xlm}} XLM in any {{fact:nested-period-ledgers}} ledgers. The grant works like a keycard that opens the game room, where the game then asks for the stake and the same card must cover it.

{{fig:fig-nested}}

The same transfer signed as its own entry has transfer as its root, so pay-game refuses it, as it refuses the transfer under another function or another game, or to anyone but the game. A win needs only the root call, because the game pays the player from its own balance. The stack's tests and the Nido simulation below run each of these cases (auth_root.rs).

The simulation below starts where a Nido user starts. You create a Nido account the way Nido does: Nido's factory deploys the account from a one-time setup key, and the account's constructor makes your passkey its administrator. Your passkey then installs the grant in the sign dialog, and you play the game or buy a coffee from a shop whose order pulls {{fact:nido-coffee-eurc}} EURC from the account in a call inside it. Each request opens the dialog, which previews it, and after you approve, the page shows each call of the tree checked against its rule. The page labels the simulated parts: a software key stands in for the passkey, Nido's factory is rebuilt to deploy this stack's account, EURC is a test token, and the game and the shop are written for the demo.
