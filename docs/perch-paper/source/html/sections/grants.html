The dialog shows every authorization the request asks for

The café's transaction calls the XLM token's transfer with the account as the sender. The token calls require_auth on the account, and because the account is a contract, the host, the program that runs contracts for the network, calls the account's __check_auth to approve {{cite:cap-0046-11,stellar-custom-account}}. A transaction carries one authorization entry for each approval it needs, and each entry holds a tree of calls, such as a game's guess that itself transfers XLM from the account. Soroban calls each such call a context, and the transaction names a rule for each one; the account checks that rule and searches for no other. The sign dialog decodes every entry from the transaction alone, with no network: it leads with what the user approves in plain words and keeps the whole tree they would authorize under Details.

The whole tree matters because a signed entry is published with its transaction. The café demo's third order comes from a tampered checkout that adds a second entry, a transfer of 4 XLM to another address, which the transaction never uses. If the user signs, anyone can submit that entry later, until it expires; in the recorded run, submitting it alone moved 4 XLM to the other address. The dialog marks the entry as unused, so the user can refuse. A grant that pins the recipient, such as the shop grant, refuses a transfer to any other address, which the dual simulation's "Pay 1 elsewhere" preset shows.

The preview shows the verdict and the budget left

Before the user signs, the dialog previews the request in the simulator. The preview records the transaction independently and flags any entry the request carries that the recording does not need. It then runs the account's own __check_auth with enforcing simulation, which gives Perch's verdict, the change in the account's balance and how much of the grant's budget remains; the recording simulation that finds a transaction's entries skips __check_auth and cannot predict a refusal. In the café demo, a 5 XLM order is accepted, and the budget left falls from 7 to 2 XLM. An 8 XLM order is refused with contract error {{fact:auth-error-rule-eval-refused}}, and the budget stays at 7 XLM.

The budget is the rule's cap. At any ledger the window is the last {{fact:shop-period-ledgers}} ledgers, and a transfer is accepted only if the window's total plus the new amount stays within the limit. The account keeps the charges in a spending record in its own storage and charges a transfer in the same decision that checks it. With JavaScript, {{ref:fig:fig-cap-window}} plays the shop grant's cap of {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers: send amounts and advance the ledger, tick "Check each call alone" to see what a per-call check would let through, or press "Replace the rule" and then send 10 to see a replaced rule start with an empty window.

{{fig:fig-cap-window}}

For the same cap and period, a sliding window is a tighter limit than one that resets on a schedule. MetaMask's delegation framework {{cite:metamask-delegation}} caps token transfers per fixed period that resets at each period's start (ERC20PeriodTransferEnforcer.sol:11-16), so an app can spend the full cap just before a reset and again just after it. A Perch window stays within its limit wherever it is placed.
