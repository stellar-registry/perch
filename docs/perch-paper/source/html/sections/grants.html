The app's transaction calls the XLM token's transfer function with the account as the sender. The token contract calls require_auth on the account, and because the account is a contract, the host (the program that runs contracts for the network) calls the account's __check_auth function with the authorization entry from {{ref:fig:fig-shop-request}} to approve the transfer {{cite:cap-0046-11,stellar-custom-account}}.

A transaction carries one authorization entry for each approval it needs. Each call in the entry's root_invocation is a context, and the transaction names a rule for each one. The account checks that rule and searches for no other. In this example, the shop payment has one context, the transfer, and the transaction names the shop grant's rule for it.

If a call leads to further calls that need the account's approval, such as a call to another contract that itself moves XLM out of the account, each of those is a context too, and the transaction names a rule for it, which it must fit.

The cap holds over a sliding window

A rule's cap is a budget over time. At any ledger the window is the last {{fact:shop-period-ledgers}} ledgers, and a transfer is accepted only if the window's total plus the new amount stays within the limit. The account keeps the charges in a spending record in its own storage and charges a transfer in the same decision that checks it. {{ref:fig:fig-cap-window}} below lets you try the shop grant's cap of {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers (it needs JavaScript).

Try it out in the simulation below.

  • Send different amounts to see which transfers the window accepts.
  • Use the Advance buttons to move the ledger forward and see the window reset, so earlier charges stop counting.
  • Tick "Check each call alone" to see what a per-call check would let through instead of taking into account the window limit.
  • Press "Replace the rule" to see what happens when the owner changes a grant. Perch never edits a rule in place: it installs a new one, and the new rule starts with an empty spending record. Send 10 XLM after replacing it, and the transfer is accepted even if the old window was full.
  • Press "Reset to the figure’s events" to go back to the transfers in the figure above, with the cap at 10 XLM per 100 ledgers and both boxes unticked. Press "Clear" to remove every transfer and start from an empty window.
  • Tick "Start at ledger 0" to see the one case the proof leaves out. Starting at ledger 0, two transfers of the full cap are both accepted, because the window never counts a transfer made at ledger 0. Stellar's ledgers start at 1, so this cannot happen on the network.

For the same cap and period, a sliding window is a tighter limit than one that resets on a schedule. MetaMask's delegation framework {{cite:metamask-delegation}} caps token transfers per fixed period that resets at each period's start (ERC20PeriodTransferEnforcer.sol:11-16), so an app can spend the full cap just before a reset and again just after it. A Perch window stays within its limit wherever it is placed.
