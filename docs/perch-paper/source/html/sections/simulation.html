OpenZeppelin's Soroban account library {{cite:oz-stellar-accounts}} composes the same decision from separate contracts. Its unit of permission is a context rule: a target such as one contract, an optional expiry, signers, and attached contracts, each a policy the account calls on every call the rule approves. oz-policy-builder {{cite:oz-policy-builder}} writes rules for these accounts. It synthesises a predicate, a condition on one call, from a recorded transaction or a declared intent, and a shared policy contract, the interpreter, evaluates the predicate on every call the rule guards. The interpreter keeps no totals. oz-policy-builder's documentation says limits over time come from a token allowance with an expiry, or from OpenZeppelin's spending_limit policy beside it (docs/stellar.md:404-407).

soroban-sim {{cite:soroban-sim}} packages soroban-env-host, the host library the network runs, so this page can run both designs' real contract code offline. It keeps one ledger per design and applies every request with enforcing authorization; its host build does not meter costs exactly. Each side runs contracts built from the pinned sources beside the native XLM contract: the OpenZeppelin {{fact:oz-v080-tag}} account, oz-policy-builder's policy-interpreter and spending_limit, whose hashes match oz-policy-builder's testnet records; or the Perch account, its document compiler and its Ed25519 verifier. On the OpenZeppelin side the shop rule is the predicate oz-policy-builder's synthesiser writes from the same intent, which pins the recipient and bounds each transfer at {{fact:sim-oz-per-call-bound-xlm}} XLM, with spending_limit at {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers beside it. The interpreter refuses external signers on the rules it polices (error {{fact:opb-error-external-signer}}), so that side signs as a delegated Stellar account, in a second authorization entry.

The recorded run shows where the designs differ

{{ref:fig:fig-sim}} replays soroban-sim's native run:

  • The app pays the shop {{fact:sim-pay-xlm}} XLM, and both accounts apply it. The further {{fact:sim-second-pay-xlm}} XLM is refused by both: Perch in its decision, with no verifier call, and the OpenZeppelin account in spending_limit (error {{fact:oz-spending-limit-exceeded}}).
  • The owner removes spending_limit from the OpenZeppelin rule. The per-call bound then applies each of {{fact:sim-oz-percall-sends}} more {{fact:sim-pay-xlm}}-XLM payments, {{fact:sim-oz-percall-moved-xlm}} XLM within a few ledgers, while Perch refuses all {{fact:sim-oz-percall-sends}} because its window already holds {{fact:sim-pay-xlm}}. Adding spending_limit back starts it with an empty history, as replacing a Perch rule starts an empty window.
  • A payment to another recipient, a signature by another key in the app's name, and a key not on the rule are refused by both. After {{fact:shop-period-ledgers}} ledgers, {{fact:sim-late-pay-xlm}} XLM goes through in both.

A Perch cap is part of its rule, so it cannot be detached on its own; removing it means replacing the rule. A reviewer reads one document and one decision function, rather than the account's checks plus every policy attached to each rule, and one owner call removes a grant across every contract it covers, where an OpenZeppelin account's rules are removed one at a time. A native run, a WASI build and this page return identical replies on every request once timings are removed; Provenance lists every contract's hash. The Aha Company publishes soroban-sim ({{fact:soroban-sim-license}}), and the authors work there.

Each design is stronger somewhere

oz-policy-builder

  • Maturity. Its interpreter is pinned on testnet, the project is under external audit, its off-chain packages were hardened after a penetration test, and it is exercised on recorded mainnet transactions.
  • Authoring. It tests that each condition of a synthesised predicate is needed and verifies the predicate against the deployed interpreter; a CLI and an MCP server expose its {{fact:opb-tools-count}} tools.
  • Expressiveness and reach. Or, comparisons, conditions over lists, clock windows, slippage floors, reads of other contracts, threshold policies and a deny code for each reason. Its installer supports existing OpenZeppelin account builds, including the 0.7.2 line in use on mainnet (policy-synth/README.md:143).

Perch

  • Limits over time. Every capped rule's decision includes its window.
  • One decision point. One contract holds the rules and their state, installs one document that covers several contracts, and accepts passkey signers on grant rules.
  • Proved decision logic. The decision function is proved in Lean to accept only what the rules allow and to keep each window within its cap.

A Perch grant needs a Perch account.
