This step runs the shop grant's payments through two accounts side by side: a Perch account and an OpenZeppelin account. Both hold the same rule: the app's key may send XLM only to the shop, at most {{fact:shop-cap-xlm}} XLM in any {{fact:shop-period-ledgers}} ledgers. The two agree on every payment while the rule is intact. They differ in how the limit is built over time. In OpenZeppelin it is a separate contract attached to the rule, and the rule keeps working without it. In Perch it is part of the rule.

OpenZeppelin's Soroban account library {{cite:oz-stellar-accounts}} builds a permission from separate contracts. Each permission is a context rule, which names what it covers, such as one contract, which signers must approve, and an optional expiry. A context rule can also have contracts attached to it, each a policy, which the account calls to check every call the rule approves. oz-policy-builder {{cite:oz-policy-builder}} writes these rules. From a recorded transaction or a stated intent, it writes a predicate, a condition on one call, and a shared policy contract, the interpreter, checks the predicate on every call the rule covers. The interpreter keeps no running totals, so a limit over time needs something else: oz-policy-builder's documentation points to a token allowance with an expiry, or to OpenZeppelin's spending_limit policy attached beside the interpreter (docs/stellar.md:404-407). This comparison uses spending_limit.

On the OpenZeppelin side, the shop rule is the predicate oz-policy-builder writes for this intent. It pins the recipient and limits each transfer to {{fact:sim-oz-per-call-bound-xlm}} XLM, and spending_limit caps the total at {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers. The interpreter does not accept external signers (error {{fact:opb-error-external-signer}}), so on that side the app signs as a delegated Stellar account, in a second authorization entry. On the Perch side, the shop grant's one rule does all of this.

The recorded run shows where the designs differ

{{ref:fig:fig-sim}} shows a recorded run in which each request goes to both accounts:

  • Both enforce the cap. The app pays the shop {{fact:sim-pay-xlm}} XLM, and both accounts accept it. A further {{fact:sim-second-pay-xlm}} XLM in the same window is refused by both: Perch in its own decision, before it checks the signature, and the OpenZeppelin account in spending_limit (error {{fact:oz-spending-limit-exceeded}}).
  • Only Perch's cap cannot be detached. The owner removes spending_limit from the OpenZeppelin rule, which shows what the rule allows without it, whether it was removed or never attached. Only the {{fact:sim-oz-per-call-bound-xlm}} XLM limit on each transfer is left, so {{fact:sim-oz-percall-sends}} more {{fact:sim-pay-xlm}} XLM payments go through: {{fact:sim-oz-percall-moved-xlm}} XLM within a few ledgers. Perch refuses all {{fact:sim-oz-percall-sends}}, because its window still holds the first {{fact:sim-pay-xlm}} XLM. Adding spending_limit back starts it with an empty history, just as replacing a Perch rule starts an empty window.
  • Both refuse the rest. A payment to another recipient, another key signing in the app's name, and a key not on the rule are refused by both. After {{fact:shop-period-ledgers}} ledgers, a {{fact:sim-late-pay-xlm}} XLM payment goes through in both.

A Perch cap is part of its rule, so it cannot be removed on its own; changing it means replacing the rule. A reviewer reads one document and one decision function, rather than the account's checks plus every policy attached to each rule. One owner call also removes a grant across every contract it covers, where an OpenZeppelin account's rules are removed one at a time.

How the comparison runs

soroban-sim {{cite:soroban-sim}} packages soroban-env-host, the host library the Stellar network runs, so this page can run both designs' real contract code in the browser, offline. It keeps a separate ledger for each account and checks authorization on every request, as the network does, though it does not measure costs exactly. Both sides run contracts built from pinned sources, next to the native XLM contract. The OpenZeppelin side runs the OpenZeppelin {{fact:oz-v080-tag}} account and oz-policy-builder's policy-interpreter and spending_limit, whose hashes match oz-policy-builder's testnet records. The Perch side runs the Perch account, its document compiler and its Ed25519 verifier. The same requests give identical replies, apart from timings, when run natively, as a WASI build and in this page; Provenance lists every contract's hash. The Aha Company publishes soroban-sim ({{fact:soroban-sim-license}}), and the authors work there.

Each design has its strengths

oz-policy-builder

  • Maturity. Its interpreter is pinned on testnet, the project is under external audit, its off-chain packages were hardened after a penetration test, and it is exercised on recorded mainnet transactions.
  • Authoring. It tests that each condition of a synthesised predicate is needed and verifies the predicate against the deployed interpreter; a CLI and an MCP server expose its {{fact:opb-tools-count}} tools.
  • Expressiveness and reach. Or, comparisons, conditions over lists, clock windows, slippage floors, reads of other contracts, threshold policies and a deny code for each reason. Its installer works with existing OpenZeppelin accounts, including the 0.7.2 line in use on mainnet (policy-synth/README.md:143). A Perch grant, by contrast, works only on a Perch account.

Perch

  • Limits over time. Every capped rule's decision includes its window.
  • One decision point. One contract holds the rules and their state, installs one document that covers several contracts, and accepts passkey signers on grant rules.
  • Proved decision logic. The decision function is proved in Lean to accept only what the rules allow and to keep each window within its cap.

The companion paper Perch and oz-policy-builder sets out every dimension with a source for each cell, and the oz-policy-builder walkthrough replays one task in both designs step by step.
