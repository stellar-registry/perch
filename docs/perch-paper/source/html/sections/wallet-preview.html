Nothing in the five steps above needs a person: the app signs and the account decides. When a person does sign, such as a user paying at a checkout, their wallet can help in two ways before they approve. It can show every authorization the transaction asks for, and it can simulate the transaction to show whether the account will accept it and how much of the grant's budget is left. We include the demo below because it shows the grant at work from the user's side. You can watch one order fit within the cap, a larger one get refused, and the budget left shrink as payments go through. The demo uses a sign dialog in a toy café app.

The dialog shows every authorization the transaction asks for

The dialog decodes the transaction itself, with no network. It first says in plain words what the user is approving, then lists every authorization entry in full under Details.

Showing every entry matters because a signed entry is published along with its transaction. The third order comes from a tampered checkout. Besides the payment, it carries a second entry authorizing a transfer of 4 XLM to another address, which the transaction itself never uses. Once the user signs, anyone can copy that entry and submit it on its own until it expires; in the recorded run, doing so moved the 4 XLM. The dialog flags the entry as unused, so the user can reject the order. A grant that pins the recipient, such as the shop grant, would refuse the extra transfer anyway, as the dual simulation's "Pay 1 elsewhere" preset shows.

The preview shows whether the account will accept, and the budget left

Before the user signs, the dialog simulates the transaction in two passes. The first pass records which authorizations the transaction actually needs, and the dialog flags any entry it carries beyond those; that is how it catches the tampered checkout. This pass alone can't predict a refusal, because recording simulation, which wallets normally use to find a transaction's authorizations, skips the account's __check_auth. The second pass is an enforcing simulation: it runs __check_auth, so it shows Perch's verdict, how the account's balance changes and how much of the grant's budget is left. In the café demo, a 5 XLM order is accepted and the budget left falls from 7 to 2 XLM. An 8 XLM order is refused with contract error {{fact:auth-error-rule-eval-refused}}, and the budget stays at 7 XLM.
