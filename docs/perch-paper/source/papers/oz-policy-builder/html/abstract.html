ABSTRACT

Perch and oz-policy-builder bound what an app may do from an OpenZeppelin-style Soroban smart account in two different ways. oz-policy-builder composes a decision from separate contracts attached to the account's rules: a shared interpreter checks each call against a predicate synthesised from a recorded transaction or a declared intent, OpenZeppelin's spending_limit keeps totals, and threshold policies count signers. Perch decides at one point inside the account, with the window cap in the same decision. We compare the two from their public documentation and source at fixed revisions, and from one task run in both in soroban-sim. Both enforce the configured window in that task. Perch integrates the window cap into its decision function and supplies proofs about the function’s Lean translation; the account shell remains tested. oz-policy-builder is stronger in maturity, authoring and expressiveness: a testnet deployment, external review, tests on real mainnet transactions, record-and-synthesise authoring, and live reads, clock windows and quantifiers. We end with what Perch should adopt from it.

At a glance

  1. Shared ground. Both use OpenZeppelin's context rules, both judge each call alone, and both deny by default ({{ref:sec:overview}}).
  2. Choose oz-policy-builder today for a design that is deployed on testnet, under external audit and tested on mainnet recordings; that adds rules to OpenZeppelin accounts already in use; for authoring by recording a transaction; and for live reads, clock windows, quantifiers and OpenZeppelin's add-ons ({{ref:sec:opb-stronger}}).
  3. Consider Perch for a spending window inside the decision, one place that decides, and a core check with machine-checked proofs. In return you take a design that is merged into Perch's dev but not yet main, runs on testnet only as a preview of an earlier build and has no audit ({{ref:sec:perch-stronger}}).
  4. Run both. The simulation page runs both accounts' real contract code side by side, offline, on requests you choose.
