oz-policy-builder is ahead on maturity, on authoring, and on what a rule can say and plug into. These are the reasons to choose it today.

Maturity

oz-policy-builder's packages pin one interpreter instance on testnet, {{fact:opb-interpreter-testnet}}, running the Wasm built from this tree ({{fact:opb-interpreter-wasm-short}}); they pin none on mainnet yet (packages/policy-synth/src/config.ts:57-80). An external audit of release {{fact:opb-release}} has been {{fact:opb-audit-status}} since {{fact:opb-audit-start}}, covering {{fact:opb-audit-scope}} (README.md:57-59, 166-171). Its off-chain packages were hardened after an external penetration test (pull request {{fact:opb-pentest-pr}}, {{fact:opb-pentest-branch}}, whose merge commit is the pin, {{fact:opb-pin-short}}).

It is tested on real transactions. A corpus test takes {{fact:opb-corpus-calls}} mainnet contract calls of {{fact:opb-corpus-shapes}} shapes, among them SEP-41 transfers, Soroswap swaps and Blend submits, from decoding through a synthesised rule to the interpreter's verdict on the call it came from, replayed offline (packages/policy-synth/src/corpus.test.ts:1-3; fixtures/corpus/mainnet.json). The interpreter has {{fact:opb-interpreter-tests}} tests, {{fact:opb-tests-against-oz08}} of them against OpenZeppelin's {{fact:oz-v080-tag}} account (docs/audit-overview.md:15-20); a worst-case suite runs its Wasm; scripted testnet runs cover the executor binding, the adapter, a no-gate liquidation and the {{fact:oz-v080-tag}} migration (evidence/README.md:10, 18-24); and mutation testing of one path gives {{fact:opb-mutants}}, the survivor equivalent (evidence/README.md:23). A STRIDE threat register gives each threat its control, how it was checked and its status (evidence/README.md:17).

Perch is behind on each count. The design compared here is an unmerged stack of pull requests ending at {{fact:perch-pr-stack-head}}, runs on testnet as a preview through the Nido wallet, and has had no external audit. Its Wasm runs in release-stack tests, a scripted reference run and {{fact:nido-run-transactions}} testnet transactions; there is no corpus of real transactions. Perch's earlier design, {{fact:perch-deployed-source-short}}, is on mainnet.

Authoring

oz-policy-builder starts from what an app did. Its synthesiser takes a recorded transaction, or a declared Intent, and writes a predicate that permits it. It verifies the result by dry-running the deployed interpreter's own check, so one evaluator both verifies and enforces, and it tests that each conjunct is needed by dropping each in turn. It reads every live rule on the account and refuses an install a shared signer could bypass through a looser neighbour, or whose rolling total such a neighbour would escape (packages/policy-synth/README.md:171). It renders a review for the owner, which names any override the owners chose, and returns unsigned install bytes. All of this is {{fact:opb-tools-count}} tools over a command-line tool and an MCP server, published to npm at {{fact:opb-packages-version}} as three packages (README.md:13-24; packages/*/package.json:3).

Perch starts from what the owner grants. A wallet or app writes a grant document, with the perch-js builder or its requestToPolicyDoc for an ERC-7715-shaped request, and the account's document compiler validates it at install. Perch's perch-analyze crate runs offline checks on documents, but Perch has no recorder and no minimality check, and checking a grant against the account's own evaluator before install is one of the proposals in {{ref:sec:lessons}}.

Expressiveness and ecosystem

oz-policy-builder adds rules to accounts already in use, with no new account code. Its installer signs for the {{fact:oz-v072-tag}}-line build that existing Prime and mainnet accounts run, and for {{fact:oz-v080-tag}} (packages/policy-synth/README.md:143; deployments/oz-accounts.json:2). A Perch grant needs a Perch account.

A predicate can say more than a Perch rule. Its grammar has and and or, six comparisons, in and nin, the quantifiers all, any and sum over vectors, checked scaled arithmetic, the ledger clock now, nested paths into arguments, and read of other contracts (contracts/stellar/policy-interpreter/src/dsl.rs:84-158), up to {{fact:opb-interpreter-max-reads}} reads per enforce on the testnet pin. An Intent can state clock windows (until, from), a swap's slippage floor (minOut), and properties of every element, some element or the total of a list (each, some, total) (packages/policy-synth/src/intent.ts:18-49). A Perch rule has a target, a function list, {{fact:doc-conditions-count}} conjunctive argument conditions, a threshold, an expiry and a window cap, and reads nothing outside the account.

It also fits the rest of the OpenZeppelin ecosystem. Thresholds come from OpenZeppelin's simple_threshold and weighted_threshold policies (README.md:122-125). A refusal reports a deny code per reason (contracts/stellar/policy-interpreter/src/storage.rs:27-86), where a Perch refusal reports only auth error {{fact:auth-error-stale-scope}} or {{fact:auth-error-rule-eval-refused}} and a wallet re-runs the evaluator off chain to learn which check failed. And OpenZeppelin {{fact:oz-v080-tag}} binds the selected rule IDs for delegated signers as well as external ones (oz8:storage.rs:157-175, 396-412); Perch binds them only for external signers, because a delegated signer approves the host's payload, which does not name them. OpenZeppelin's spending_limit can change its limit in place and keep its history (oz8:policies/spending_limit.rs:340-365; the example contract exposes it, oz8:examples/multisig-smart-account/spending-limit-policy/src/contract.rs:79-85); changing a Perch cap starts an empty record (Perch docs/DEFERRED.md:298-324).

The design also has shapes Perch lacks. A keyless rule bound to an execution adapter lets anyone run, for example, a liquidation the predicate permits (docs/architecture.md:149). A rule may follow another account's rule, so an issuer governs a borrower's limits (docs/audit-overview.md:249-254). And an adapter batch can wait before it runs, while one predicate relates its calls (docs/stellar.md:125-140, 350-352).
