Perch and oz-policy-builder bound what an app or agent may do from an OpenZeppelin-style Soroban account. oz-policy-builder composes the bound from separate contracts; Perch decides it at one point inside the account.

This paper compares the two designs in both directions: where oz-policy-builder is stronger, where Perch is, and what Perch should take from oz-policy-builder. It is a companion to the Perch paper, which describes Perch's grants and what is proved about them, but it stands alone and repeats what it needs.

Shared ground

  • The same rule model. OpenZeppelin's account checks each context against the context rule the signer names for it in context_rule_ids, with External or Delegated signers. oz-policy-builder attaches to those rules; Perch reproduces the field and the signer kinds and attaches nothing.
  • Each call is judged alone. The interpreter "sees one authorised call at a time" (docs/architecture.md:307-309), and Perch checks each context against its own rule. In both, a rule written for the transfer a game makes also allows that transfer made directly.
  • Both deny by default. The interpreter is "fail-closed" (README.md:21-24) and its predicates have no not. A Perch account accepts a context only when the rule named for it allows it.
  • Neither lets an app's rule reach the account's administration. The interpreter refuses a Default scope, or a rule scoped to the account or to itself (error {{fact:opb-error-default-context}}; policy-interpreter/src/lib.rs:103-114). Perch refuses a grant rule whose target is the account, its adopted recovery controller, or the zero-knowledge adapter and pool of its recovery configuration ({{ref:stmt:grant-target-containment}}).

The trade-off

oz-policy-builder composes. A shared interpreter checks each call against a stored predicate, OpenZeppelin's spending_limit keeps totals, and a threshold policy counts signers. Each is a contract that can be reused, replaced and audited on its own, and a new combination of constraints is data, not code. In exchange, a property that spans calls or signers holds only while the right policy is attached, and the decision's state lives in several contracts. Perch puts one document behind one decision point: the rules, spending records and grant generation live in the account, and one function decides. In exchange, its rule language is smaller and its implementation is younger and unaudited.
