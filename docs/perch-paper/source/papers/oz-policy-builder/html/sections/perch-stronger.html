Perch is ahead where a limit must hold over time, where one place should decide, and where the core check should be proved. Each point comes with what it does not cover.

A limit over time, inside the decision

A Perch rule may carry a cap of λ per P ledgers, which the evaluator charges in the same decision that checks the call; a refusal changes nothing. {{ref:stmt:cap-window-safety}} proves that, from empty records, the accepted charges to a capped rule in any window (L − P, L] sum to at most λ, however the app times its payments. The bound belongs to the rule, so it holds while the rule keeps its cap.

In oz-policy-builder the total is a separate, opt-in policy. OpenZeppelin's spending_limit keeps a window with the same boundary, but nothing in the interpreter ties a rule to it (though the installer refuses a total a shared signer could bypass), and the synthesiser attaches it only on transfer (docs/stellar.md:404-407; packages/policy-synth/src/install.ts:957-967). The recorded dual simulation shows the difference: after the owner removes spending_limit, the per-call bound applies {{fact:sim-oz-percall-sends}} {{fact:sim-pay-xlm}}-XLM sends and {{fact:sim-oz-percall-moved-xlm}} XLM leave the account, while Perch refuses all three ({{ref:sec:same-task}}). The owner chose that configuration, and oz-policy-builder documents it; the difference is where the guarantee lives.

What it does not cover. The theorem is about the evaluator's Lean translation, from empty records; rule selection and record persistence in the account are tested. Caps are per rule, not per grant, and replacing a capped rule starts an empty window. One spending record holds at most {{fact:spends-per-window}} spends per window. A Perch document cannot bound a single call's amount.

One decision point

  • State in one contract. The rules, the spending records and the grant generation are in the account's storage; no other contract keeps part of the decision.
  • Decide, then authenticate. The whole decision, cap included, runs before any verifier is called, so a refused request calls no verifier, and nothing is written unless the signatures also check (crates/perch-smart-account/src/gate.rs:93-113).
  • One install across contracts. A grant whose rules name several contracts installs with one apply_scope call; the threshold is part of each rule.
  • Passkeys on grant rules. A grant rule may hold an external signer, such as a passkey checked by a WebAuthn verifier contract, or a delegated one. oz-policy-builder's policed rules take delegated signers only: its interpreter authorizes signers with require_auth, which an external signer's verifier never satisfies (policy-interpreter/src/lib.rs:451-462).

What it does not cover. One decision point is also one place that must be right. A delegated signer does not bind the selected rule IDs. A refusal reports only one of two codes. And an account cannot add someone else's policy beside its rules.

A proved core

The decision function, about {{fact:rule-eval-lines}} lines of no_std Rust in rule-core, is translated into Lean by Charon {{cite:charon}} and Aeneas {{cite:aeneas}}. Lean's kernel {{cite:lean4}} has checked that the translation returns what a readable model returns on every input, without panicking or looping ({{ref:stmt:total-equivalence-of-the-evaluator}}); that when the decision function accepts, each call is allowed by some rule it was given ({{ref:stmt:acceptance-implies-permission}}); that attenuation never widens the calls a grant allows ({{ref:stmt:attenuation-narrows-authority}}); the window bound ({{ref:stmt:cap-window-safety}}); and that no installed grant, nor one derived from it, allows a call to the account or its adopted recovery contracts ({{ref:stmt:grant-target-containment}}). What Perch proves has all thirteen theorems. For oz-policy-builder, the evidence is tests, partly on the shipped Wasm, and a STRIDE register; we found no formal model in its tree.

What it does not cover. The proofs are about the Lean translation, not the compiled Wasm, and nothing checks one against the other. The account code around the function is tested. Attenuation is modelled and proved, but the account cannot install an attenuated grant at the pinned build. Nothing is audited.

Stopping every earlier grant

Each installed grant is stamped with the account's grant generation, which only a completed recovery advances. After one, every earlier grant stops authorizing through the account: it refuses every request with a call in it, from the completion transaction on. Allowances a grant created stay usable. This is proved in rule-core's account model ({{ref:stmt:recovery-invalidation}}), tested, and run on testnet (the Perch vision). OpenZeppelin rules are removed one at a time. What it does not cover: the account model has no Rust counterpart, passing the generation in is tested shell code, and outside a recovery the owner also removes Perch grants one at a time.
