Written in both languages, one intent shows where they differ: where the window lives, how rules are installed, who may sign, and what a rule may consult.

{{ref:fig:fig-two-spellings}} writes one intent both ways. It is the game grant that the Nido wallet's testnet preview installed: the app key may call guess on the game, and may send XLM only to the game, at most {{fact:preview-game-cap-xlm}} XLM per {{fact:preview-game-period-ledgers}} ledgers ({{fact:preview-game-period-label}}), through ledger N − 1. We read the oz-policy-builder side from source and did not run its installs. The numbered notes match the marks in the figure.

{{fig:fig-two-spellings}}
  1. Both systems select one rule per context, and each rule sees its own call alone (docs/architecture.md:307-309). So in both, a transfer to the game is allowed without a guess.
  2. In Perch the window cap is part of the rule. oz-policy-builder turns the Intent's cap into a per-call lte and attaches spending_limit for the window, because the interpreter keeps no totals (contracts/stellar/policy-interpreter/src/dsl.rs:65-72). A Perch document cannot bound a single call's amount; its window limit is its only amount bound.
  3. Perch installs both rules in one transaction. oz-policy-builder builds one add_context_rule per install_policy call (packages/policy-synth/src/tools.ts:588-590).
  4. Perch's grant rule holds a passkey as an external signer. oz-policy-builder writes every rule signer as Delegated (install.ts:148), and the interpreter refuses External signers with error {{fact:opb-error-external-signer}}, so an oz-policy-builder app signs as a Stellar or contract address. Its install is authorized by sourceAccount, which must be a signer of rule 0, the owners' rule; a Perch install needs the owner's authorization in the account's own entry.
  5. Expiry: in Perch, {{fact:perch-expiry-semantics}}. OpenZeppelin's valid_until authorizes through itself (oz8:storage.rs:321-322), so validUntilLedger: N − 1 names the same last ledger.
  6. oz-policy-builder can consult live state, for example a read of a registry before permitting a recipient (docs/stellar.md:369-375); a Perch rule reads nothing outside the account. A Perch grant ends when the account recovers. oz-policy-builder has no account-key recovery; the "recovery" of its Prime product moves custody funds to a fixed address (docs/architecture.md:81-94).

Starting from a recording

oz-policy-builder can also start from a recorded transaction. Its registry of known protocols turns a recording into an Intent: who is pinned, what is capped, what is asked (packages/policy-synth/README.md:50-51). For a function the registry does not know, every argument that is not an amount is pinned to its recorded value (src/synth.ts:62-86). guess is not in the registry, so a recorded lost guess would pin the guessed number; we derived this from source and did not run it. Verification then puts the rule to the deployed interpreter's check, derives deny cases, and drops each conjunct in turn to test minimality, listing what it could not examine (policy-synth/README.md:52-64). A recording shows one call. It cannot show a total, an expiry or the account's other rules, which is why spendingLimit and validUntilLedger are install inputs and the overlap scan reads every live rule on the account (policy-synth/README.md:176).
