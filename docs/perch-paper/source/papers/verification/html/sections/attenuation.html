Attenuation narrows a grant step by step. Two theorems say a derived grant allows no call its parent does not, and accepts no run from empty records that its parent would refuse. The account cannot install an attenuated grant at the pinned build.

Attenuation derives a narrower rule set from an existing one, for example to hand part of an app's authority to a helper. rule-core defines exactly {{fact:attenuation-steps}} attenuation steps ({{ref:tab:tab-attenuation}}); each returns a rule set that allows no call the original does not, and none changes a rule's target or generation. A move no step allows, such as raising a limit or shortening a period, is refused, not approximated.

{{statements:T4,T5}}

{{ref:stmt:attenuation-narrows-authority}} is about single calls: under any signers, whatever the child allows, the parent allows. allows reads no cap or expiry, so the steps that add or tighten those narrow only over runs. {{ref:stmt:trace-inclusion}} is about histories: any run the child accepts from empty records, the parent accepts from its own empty records, with each rule choice renumbered past the rules a step dropped. It covers one derivation lineage, not two sibling grants spending together, and since parent and child keep separate records, neither theorem bounds what the two spend together. Both are proved for the model and the translation. They are results about rule-core: no Perch entry point installs an attenuated grant at {{fact:perch-pin-short}}, and one is proposed (the Perch vision).
