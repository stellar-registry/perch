Every theorem in this paper was checked by Lean's kernel, and each is about one named object. None is about the compiled contract.

A Perch account decides each authorization with one function, rule_eval::authorize in the rule-core library {{cite:rule-core}}. It takes the selected rules, their spending records, the calls, one rule index per call, the claimed signers, the ledger number and the account's grant generation, and returns the next spending records or a refusal; it reads no storage and checks no signature. The contract code around it, the account shell, stores state, selects the rules and checks signatures. The Perch paper explains what that function decides and shows five of the theorems about it. This companion gives all of them, with the definitions they rest on, and says what carries them to the deployed account and what they leave out.

Five objects

Each statement names what it is about:

  • the model, rule-core's readable Lean definitions of rules, authorization and lowering ({{ref:sec:definitions}});
  • the translation, the Lean program that Charon and Aeneas generate from the Rust ({{ref:sec:pipeline}});
  • the account model, an abstract account with two events, apply a document and complete a recovery, and no Rust counterpart ({{ref:sec:account}});
  • the host model of Soroban's authorization, whose fidelity to the real host is tested ({{ref:sec:host}});
  • Perch's canonical-encoding package, a separate Lean development in Perch's repository ({{ref:sec:obligations}}).

Aeneas gives every translated function three outcomes: success, failure (a Rust panic) and divergence. A theorem that a function succeeds on every input therefore proves that it neither panics nor loops; Rust's Result<_, Refusal> is the value inside that success. This paper says proved only of statements Lean's kernel has checked. rule-core's CI pins the axioms of all {{fact:exported-theorems}} exported theorems, and none uses more than Lean's three standard axioms ({{fact:standard-axioms}}), so none uses sorry, Lean's placeholder for a missing proof, or an axiom of its own. A claims ledger, also checked in CI, records {{fact:claims-total}} claims as proven ({{fact:claims-proven}}), tested ({{fact:claims-tested}}), assumed ({{fact:claims-assumed}}) or unproven ({{fact:claims-unproven}}); {{ref:sec:trust}} lists the assumed and unproven ones.

How to read a statement card

  • Head and tag. "Theorem 6 (Cap-window safety)". Numbers are shared by every Perch paper. The tag in the Lean line says what is proved about what: PROVED · TRANSLATION is a theorem about the Aeneas translation; MODEL + TRANSLATION, the property proved for the model and for the translation; ACCOUNT MODEL, HOST MODEL and PERCH CANON PACKAGE, theorems about those objects.
  • Formula, then words. The formula is the statement in the paper's notation ({{ref:sec:definitions}}); "In words" reads it in one plain line, and "Precisely" states it in full.
  • Hypotheses. Some theorems assume Doc.Valid, that the document is well formed in the sense the theorems define, or LowerRoom and ArgsRoom, that its lists fit the evaluator's bounded vectors ({{ref:sec:documents}}).
  • Try an instance. Where it helps, an instance runs a small model of the definitions in the page, so you can pick inputs and watch the property hold. It is a model computed here, not the contract.
  • Lean. The Lean names, linked to their lines at rule-core {{fact:rule-core-pin-short}} or Perch {{fact:perch-pin-short}}.
  • Borders. Double for a theorem, single for a definition, dashed for the one argued proposition, which is not mechanized.
