The proofs rest on a kernel, a translation toolchain and a specification written by hand. The deployed account rests on more.

What the proofs trust

  • Lean's kernel and its three standard axioms, {{fact:standard-axioms}}.
  • Charon {{fact:charon-rev}}, Aeneas {{fact:aeneas-rev}}, and Aeneas's Lean library, which models Rust's primitives.
  • The MIR that rustc {{fact:rustc-mir-nightly}} produces.
  • The specification: the denotation functions ({{ref:def:denotation}}), and the document meaning Doc.allows, written from Perch's earlier account at {{fact:doc-allows-source}}.
  • The host models, tested against {{fact:host-model-tested-versions}}.

The deployed account also relies on rustc {{fact:rustc-perch}} and its WebAssembly back end, which build the contract; the document compiler, which turns grant JSON into the model the account lowers; the tested account shell, verifiers and recovery controller; and soroban-env-host ({{ref:fig:fig-proof-paths}}).

Cryptographic assumptions

The binding lemma assumes an EUF-CMA-secure scheme and a collision-resistant SHA-256, and {{ref:stmt:canonical-identity}} gives hash identity only up to SHA-256 collisions. Ed25519 {{cite:rfc8032}} signatures are checked with strict verification. P-256 signatures are ECDSA with low S enforced; the WebAuthn verifier {{cite:webauthn2}} checks neither the relying-party ID nor the origin. {{fact:mldsa-verifier}} is pure FIPS 204 {{cite:fips204}} with a fixed context string, the key being the hash of the public key. The compiler requires each external key to use its verifier’s canonical form. Thresholds count distinct configured signer identities: an external identity is the pair (verifier address, canonical key), and a delegated identity is an address ({{ref:stmt:signer-accounting}}). Distinct identities can share a physical key or controlling party, so independent custody is an authoring assumption. The deployed Ed25519 and WebAuthn verifiers trap on a bad signature ({{fact:verifier-trap-error}} for Ed25519) rather than return false; the built {{fact:mldsa-verifier}} verifier returns false for a well-formed failing signature. A grant may name a verifier by address alone; each such verifier may supply at most one signer per rule. Ed25519, P-256 and BN254 are not post-quantum, and administrative signers, guardians and the zero-knowledge factor can each change the account's rules, so an {{fact:mldsa-verifier}} signer resists a quantum adversary only if every such path does. A contract ID commits to its deployer and salt, not its code, so calling fixed infrastructure code assumes that the registry deploys each pinned Wasm hash at the salt derived from it and that those contracts cannot replace their code.

The zero-knowledge recovery factor proves knowledge of a secret enrolled as a Poseidon2 commitment in a depth-{{fact:zk-pool-depth}} pool, with an UltraHonk proof with KZG commitments over BN254 against a fixed setup point and Fiat–Shamir with Keccak; Perch's docs/zk/ does not name the setup ceremony. The commitment is public, so the secret must be a uniform field element with at least {{fact:zk-secret-entropy-bits}} bits of entropy. Perch's zero-knowledge verifier has not been audited. None of these assumptions enters a Lean theorem; they bear on the account, and on Lemma 1 ({{ref:sec:obligations}}).
