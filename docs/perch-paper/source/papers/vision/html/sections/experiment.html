This page runs Perch's built account, document compiler, Ed25519 verifier and recovery controller offline, and every result it shows comes from the contracts, never from the page.

The experiment runs the contract WebAssembly inside soroban-sim {{cite:soroban-sim}}, itself a WASI reactor in a browser worker, on a local protocol-{{fact:sim-protocol}} ledger. No wallet, real credential, RPC request or network transaction is involved. Each control sends a JSON command to a Rust driver, and the page shows what the runtime returns. It predates the dual simulation in the Perch paper, which runs Perch beside an OpenZeppelin account; this one runs Perch alone, but all of it, recovery included.

Three grants and a game

Suppose a player keeps XLM in a Perch account and opens Guess the Number {{cite:guess-the-number}}, a Soroban game that takes {{fact:game-wrong-guess-xlm}} XLM for each wrong guess and pays out its balance on a right one. The experiment installs three grants:

  • Grant 1, the demo's "original app", may transfer at most {{fact:grant1-cap-xlm}} XLM in any {{fact:grant1-period-ledgers}}-ledger window, {{fact:grant1-period-minutes}} at the nominal {{fact:nominal-ledger-seconds}}-second ledger. A {{fact:grant1-spend-applied-xlm}}-XLM transfer is applied; a further {{fact:grant1-spend-refused-xlm}} XLM in the same window is refused.
  • Grant 2 gives that app a fresh key after the owner recovers the account.
  • Grant 3 lets the game's app key call guess and transfer at most {{fact:grant3-cap-xlm}} XLM per {{fact:grant3-period-ledgers}} ledgers from the account, to any recipient (it pins none), so two lost guesses fit and a third is refused.

This is grant 1 as the experiment installs it, with addresses and the key abbreviated; network is the passphrase of a local standalone network. scope is the rule target, here the native XLM contract. principals is the signer condition, here the one signer app. cap.limit is {{fact:grant1-cap-xlm}} XLM in stroops ({{fact:stroops-per-xlm}} to the XLM) as a decimal string; the cap charges the amount argument of transfer(from, to, amount), and a rule may carry a cap only if its functions are exactly ["transfer"]. The signer names its verifier by address alone, which Perch treats as unverified ({{ref:sec:stack}}). Unlike the Perch paper's shop grant, grant 1 pins no recipient.

The reference run

The reference run executes {{fact:run-commands}} commands against the built account, document compiler, Ed25519 verifier and recovery controller. {{ref:tab:tab-run}} lists each command's expected result. The native command-line program and the browser build use the same Rust driver and pinned contract bytes, and they agree on every returned field but wall-clock time. Between them, the commands submit {{fact:run-transactions}} transactions: command 1 submits {{fact:run-setup-transactions}} for setup, command 19 submits {{fact:run-game-deploy-transactions}} to upload and deploy the game and one to install grant 3, and each other applied command submits one. Another {{fact:run-refused-in-simulation}} operations are refused in enforcing simulation, never submitted, and leave the ledger entries unchanged; {{fact:run-view-only}} command only advances the ledger. The run ends with {{fact:run-final-balance-xlm}} demo XLM ({{fact:run-balance-path}}) and grant generation {{fact:run-final-generation}}.

To follow {{ref:tab:tab-run}} below, create the account and work through the four groups in order. Completion is allowed from {{fact:recovery-delay-ledgers}} ledgers after the second guardian approval, so advance {{fact:demo-advance-ledgers}} ledgers before completing. Group 4 calls the actual Guess the Number contract, whose secret is drawn from {{fact:game-secret-range}}, so a guess of {{fact:game-losing-guess}} always loses; its winning-number helper reads the simulator's storage and is a harness fixture, not a game method. Then change the inputs: another cap or window, other amounts, a missing or wrong credential, or a JSON command of your own.

Method

Setup loads protocol-{{fact:sim-protocol}} cost and configuration entries from a testnet fixture (ledger {{fact:fixture-ledger}}; testnet now runs protocol {{fact:testnet-protocol}}) with the standalone passphrase and fresh local identities. It places the compiler and the Perch {{fact:perch-deployed-account-version}} policy contracts at the addresses the account derives from its build-time pins. A {{fact:registry-stub-bytes}}-byte registry stub returns the Ed25519 verifier hash for any requested version, so the account document can name its verifier {{fact:sim-verifier-name}} offline; the production registry's governance and version resolution are not tested. Grant documents name the verifier by address. Signers are software Ed25519 keys, and recovery uses real guardian signatures; no zero-knowledge or passkey flow runs.

The driver does not submit a refusal it catches during enforcing preflight, so the unchanged-state observation includes that preflight behaviour; it is not a claim that a failed, submitted network transaction pays no fee. After each step the page shows a ledger-entry fingerprint: a hash over the sorted keys, entry XDR (Stellar's binary encoding) and live-until values of every entry the session has written. It does not cover the simulator's clock, so advancing ledgers can change validity without changing the fingerprint.

An earlier build on Stellar testnet

This run used the earlier preview deployment, built from Perch {{fact:perch-preview-source}} before the pin. On {{fact:nido-run-date}} a scripted browser run of the Nido preview, with virtual passkeys, made {{fact:nido-run-transactions}} successful testnet transactions across a user account and a guardian account: account creation; an account document adding a delegated administrative signer and naming the passkey verifier {{fact:verifier-name-webauthn}}; the game's two-rule grant, whose transfer rule pays the game alone; two lost guesses; and a one-guardian Loss recovery through to completion. The completion replaced the passkey and moved the grant generation to {{fact:completion-grant-generation}} and the recovery generation to {{fact:completion-recovery-generation}}. The wallet declined a third guess before signing because it would exceed the cap: that refusal was the wallet's, not the chain's. The game ran from a development branch with an uncommitted patch.

What it costs: Perch alone

{{ref:tab:tab-run}} gives the host CPU instructions of each applied transaction, including __check_auth and verifier calls, and the table above repeats them as the page measures them. The host applies with enforcing authorization but is simulation's recording-mode build, not the exact-metering one, so counts can differ from stellar-core's metering. On the testnet preview, a fresh account holding the game's two-rule grant after two capped transfers stores {{fact:census-bytes}} bytes in {{fact:census-entries}} ledger entries, {{fact:census-rent-xlm-year}} XLM a year in rent at the network's floor rate. In a smoke test on the same deployment, an XLM transfer of {{fact:smoke-amount}} through a grant rule, signed by a passkey, declared {{fact:smoke-cpu}} CPU instructions and paid a fee of {{fact:smoke-fee-stroops}} stroops; that figure includes WebAuthn verification.

These are Perch's numbers alone, from different hosts and shapes, and they are not comparable with each other or with any other system. The limits of this evaluation: the counts are not exact-metered, testnet is reset periodically, the testnet game ran with a local patch, and one host version was used.
