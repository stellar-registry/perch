Before the evaluator decides, the account runs four guards; after it accepts, the account authenticates every signer and only then writes.

Soroban calls the account's __check_auth, which calls the account-shell function perch_smart_account::check_auth. That function runs the guards below and then the evaluator, rule_eval::check_auth in rule-core {{fact:rule-core-pin-short}}. The evaluator neither searches for rules nor verifies signatures; the shell does both. The evaluator's distinct refusals reach the host as two codes: a stale grant becomes StaleGrant (auth error {{fact:auth-error-stale-grant}}) and every other refusal RuleEvalRefused (auth error {{fact:auth-error-rule-eval-refused}}), inside {{fact:host-auth-error}}; a wallet that needs the reason re-runs the evaluator off chain.

Four guards

{{ref:fig:fig-check-auth}} traces one authorization in nine steps. Four guards run before any rule is read: reserved hook names are refused on any contract (step 1); a recovery completion is recognized (step 2); while a recovery under the Protected profile, which assumes the owner's key may be stolen, holds the account, everything but its completion is refused (step 3); and each selected grant rule is checked against the account's current excluded set (step 4). A completion leaves at step 4 and is decided by the recovery controller, so a recovery completion never depends on the evaluator.

Step 4 is the runtime half of containment. The account may adopt a recovery controller after a grant is installed, so __check_auth compares each selected grant rule's call with the excluded set as it is now and refuses with GrantEscalation (auth error {{fact:auth-error-grant-escalation}}). The install-time property has theorems; this recheck is tested shell code.

{{fact:reserved-hook-count}} reserved hook names ({{fact:reserved-hook-names}}) are refused on every contract before any rule is read, so the recovery controller's hooks are reachable from the account's own code and from nowhere else. install, uninstall and enforce are OpenZeppelin's policy hook names. A recovery completion carries no signatures, so anyone may submit and pay for it; selecting the recovery rule in any other shape is refused.

What a signature binds

For the original address credential, the host's signature payload does not name the account; CAP-0071's address-bound credentials {{cite:cap-0071}} add it. Perch binds the account either way. The account hashes the payload with its own {{fact:contract-id-bytes}}-byte contract ID under the domain tag {{fact:auth-domain-tag}}, so two accounts that share a key and rule IDs cannot reuse each other's signatures; it then appends the selected rule IDs and hashes again. An external signer signs that digest, so a relayer cannot move the signature to another rule the signer belongs to, such as an uncapped one.

A delegated signer never sees that digest. It approves the host's address-bound payload, which names the account but not the rule IDs, so whoever submits the transaction may select any rule that lists the delegate. OpenZeppelin {{fact:oz-v080-tag}} binds the rule IDs for delegated signers too, so on that path it binds more than Perch. A document should not place one delegate in rules of different strength and expect the weaker rule to bind it. What Perch proves sets the two designs side by side in a table and gives the binding lemma, a paper proof.

Unions, edits and order

A credential's authority is the union of every live rule that names it. Binding the rule IDs stops a relayer, not the signer, from choosing among those rules. The digest names rule IDs, not rule contents or the account's revision, so a rule the owner edits in place between signing and inclusion decides under its new contents; wallets should keep signature expirations short. A removed or replaced rule fails closed, because rule IDs are never reused. apply_grant takes no expected version, so two pre-signed installs for one grant ID can land in either order before they expire.
