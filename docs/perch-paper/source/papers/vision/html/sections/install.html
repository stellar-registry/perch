Installing a grant takes two contracts: a stateless compiler that checks the JSON, and the account, which lowers it into rules under its own authority and stores them.

Perch has two kinds of JSON document. An account document sets the owner's own policy: administrative rules, signers and recovery configuration. A grant document describes a bounded set of rules for an app. Installing a grant document creates or replaces an installed grant: rules and metadata stored under a grant ID and stamped with the current grant generation, a counter that only a completed recovery advances. The document is an input and a hash commitment; the installed grant is the permission the account consults.

The seven install steps

  1. The owner authorizes apply_grant ({{ref:tab:tab-api}}). The account calls the document compiler, which parses and validates the JSON, resolves verifier names through the perch/verifiers registry, and returns canonical bytes, their hash doc_hash, a model of the document, credential fingerprints and a normal-form flag.
  2. The account refuses with GrantEscalation a grant that configures recovery, and reads its excluded set: its adopted recovery controller, and the zero-knowledge adapter and pool of its recovery configuration.
  3. It lowers the model with rule-core's lower_scoped under its own address, the excluded set and the current grant generation. The lowering and containment theorems cover this function ({{ref:stmt:grant-target-containment}}, {{ref:stmt:the-containment-chain}}, {{ref:stmt:lowering-equivalence}}). A refusal surfaces as GrantEscalation, or as UnguardedRule for a rule with no signer.
  4. It refuses with NotNormalForm a document that is not in normal form, which allows one spelling per meaning.
  5. It refuses with RevokedCredential or WipedCredential a credential that a recovery revoked or that a stale grant named.
  6. It reconciles rules by name and drops the spending records of removed or changed rules.
  7. It stores the grant record, rule tags and index entry. Spending records are separate entries that only authorization writes.

Grant lowering refuses a document that configures recovery, and any rule whose target is the account, its adopted recovery controller, or the zero-knowledge adapter and pool of its recovery configuration (lib.rs:1218-1240, 1328-1345).

What the account stores

The account stores no grant JSON. A grant's rules and the metadata to rebuild it (generation, document hash, signer IDs and verifier names) share one persistent record; an index enumerates grants, and rule tags connect a selected rule ID to its grant. Because the account accepts documents only in normal form, a client can rebuild the canonical JSON from chain state and check it against the stored doc_hash, the SHA-256 of the document's CANON v1 bytes. Account document bytes are kept on chain, because recovery derives its target document from them.

CANON v1 is Perch's canonical JSON: RFC 8785 {{cite:rfc8785}} restricted to what Perch documents contain. A Lean package in Perch proves the encoding injective on the modeled document type ({{ref:stmt:canonical-identity}}). The CANON version is not part of the hashed bytes, so a doc_hash is read under the identity the account reports (capabilities().doc_identity), and three further theorems prove that configuration, rule and document hash preimages never coincide.
