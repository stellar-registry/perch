A Perch account holds its rules, grants and spending records itself, decides with a linked library, and calls out only to verifiers, the document compiler and its recovery controller.

{{ref:fig:fig-parts}} shows the parts at the pinned build. The owner signs with a passkey through a wallet; an app signs with its own grant key. For each authorization the Soroban host calls the account's __check_auth. Inside the account, the linked library rule_eval decides authorizations (authorize) and turns documents into stored rules (lower, lower_scoped). Every rule, grant and spending record lives in the account's own storage. Calls leave the account to a verifier contract on every authorization, to the document compiler on every install, to the recovery controller on account-document writes, upgrades, cancellations and completions, to the zero-knowledge pool at enrollment, and to any contract through an owner-authorized execute.

Verifiers

An external signer pairs key material with a verifier, a contract implementing verify(digest, key, signature) -> bool. Ed25519 {{cite:rfc8032}} and WebAuthn {{cite:webauthn2}} (passkey) verifiers are deployed; a verifier for {{fact:mldsa-verifier}} {{cite:fips204}}, a post-quantum signature scheme, is built and tested but in neither manifest. The shell authenticates every claimed signer, which is the evaluator's assumption. Both deployed verifiers trap on a bad signature rather than return false, so a failed signature fails in the host's signature check ({{fact:verifier-trap-error}} for Ed25519); ExternalVerificationFailed ({{fact:oz-error-external-verification-failed}}) is raised only for a verifier that returns false, as the built {{fact:mldsa-verifier}} verifier does. One {{fact:mldsa-verifier}} signer does not make an account post-quantum: the owner's passkey, Ed25519 guardians and the zero-knowledge factor are not. The compiler refuses any key not already in its verifier's canonical form, so one key has one spelling, and a threshold, which counts distinct identities byte for byte, cannot count it twice. The WebAuthn verifier checks the assertion type, the challenge, the user-presence, user-verification and backup flags and the P-256 signature, but not the relying-party ID or origin, the fields that tie a passkey to a website; binding a passkey to a site is the wallet's and authenticator's job.

Fixed infrastructure and the verifier registry

The account derives each infrastructure address, the document compiler's among them, under the current network ID from a Wasm hash and registry path fixed at build time; the derivation calls nothing. Once the pinned code is deployed on a network, no registry action changes it, and an account reaches a new compiler only through its own delayed upgrade. A Soroban contract ID commits to its deployer and salt, not to its code, so this rests on two assumptions: that the registry deploys each pinned Wasm hash at the salt derived from it, and that the deployed infrastructure contracts cannot replace their code.

An account document must name each verifier through the perch/verifiers registry, for example {{fact:verifier-name-webauthn}}. A verified name means the registry deployed that code at its own hash; its manager decides which hashes it deploys, and its admin can replace the registry's code. One key holds both roles on testnet and mainnet. A grant document may name a verifier by address alone; each such verifier may supply at most one signer per rule.

Pins left from the earlier design

The account still pins the addresses of the two Perch {{fact:perch-deployed-account-version}} policy contracts, perch_interpreter and perch_spending_limit, and reports them through infra(), but never calls them. They belong to the earlier, attached-policy design. Despite the names, they are neither oz-policy-builder's policy-interpreter nor OpenZeppelin's spending_limit.
