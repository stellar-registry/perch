ABSTRACT

This companion sets out what is proved about Perch, and about which object. Perch's authorization decision is a Rust function in the rule-core library, written in a subset that Charon and Aeneas translate into Lean. We give the definitions and all thirteen statements: the translation's equivalence with a readable model; acceptance implies permission; signer accounting; attenuation and trace inclusion; cap-window safety; delegation-tree budgets; grant containment and the containment chain; recovery invalidation in an account model; a host model of Soroban authorization; lowering equivalence; and canonical identity. Each comes with its hypotheses, its Lean names at a fixed revision and, where it helps, an instance to try. We then list the obligations on the account code around the evaluator that carry the theorems to the deployed account, the argued proposition they support, what the proofs trust, and what remains unproved.

At a glance

  1. Proved means kernel-checked. Every theorem here is a Lean statement that Lean's kernel has checked, using only Lean's three standard axioms (§01).
  2. Each theorem names its object. Most are about the readable model and the Lean translation of the Rust; one is about an account model, one about a host model, one about Perch's canonical encoding. None is about the compiled Wasm (Figure 1).
  3. The account is tested, not proved. Eight obligations of the account shell, the code around the decision function, carry the theorems to the deployed account; seven are tested or argued, and one is unproven (§10).
  4. Numbers are shared. Theorem and definition numbers are the same in every Perch paper; the Perch paper shows Theorems 1, 2, 4, 6 and 8, and this one shows all thirteen.

01What is proved, and about what

Every theorem in this paper was checked by Lean's kernel, and each is about one named object. None is about the compiled contract.

A Perch account decides each authorization with one function, rule_eval::check_auth in the rule-core library [1]. It takes the selected rules, their spending records, the calls, one rule index per call, the claimed signers, the ledger number and the account's grant generation, and returns the next spending records or a refusal; it reads no storage and checks no signature. The contract code around it, the account shell, stores state, selects the rules and checks signatures. The Perch paper explains what that function decides and shows five of the theorems about it. This companion gives all of them, with the definitions they rest on, and says what carries them to the deployed account and what they leave out.

Five objects

Each statement names what it is about:

  • the model, rule-core's readable Lean definitions of rules, authorization and lowering (§03);
  • the translation, the Lean program that Charon and Aeneas generate from the Rust (§02);
  • the account model, an abstract account with two events, apply a document and complete a recovery, and no Rust counterpart (§08);
  • the host model of Soroban's authorization, whose fidelity to the real host is tested (§09);
  • Perch's canonical-encoding package, a separate Lean development in Perch's repository (§10).

Aeneas gives every translated function three outcomes: success, failure (a Rust panic) and divergence. A theorem that a function succeeds on every input therefore proves that it neither panics nor loops; Rust's Result<_, Refusal> is the value inside that success. This paper says proved only of statements Lean's kernel has checked. rule-core's CI pins the axioms of all 940 exported theorems, and none uses more than Lean's three standard axioms (propext, Quot.sound, Classical.choice), so none uses sorry, Lean's placeholder for a missing proof, or an axiom of its own. A claims ledger, also checked in CI, records 180 claims as proven (107), tested (40), assumed (19) or unproven (14); §11 lists the assumed and unproven ones.

How to read a statement card

  • Head and tag. "Theorem 6 (Cap-window safety)". Numbers are shared by every Perch paper. The tag in the Lean line says what is proved about what: PROVED · TRANSLATION is a theorem about the Aeneas translation; MODEL + TRANSLATION, the property proved for the model and for the translation; ACCOUNT MODEL, HOST MODEL and PERCH CANON PACKAGE, theorems about those objects.
  • Formula, then words. The formula is the statement in the paper's notation (§03); "In words" reads it in one plain line, and "Precisely" states it in full.
  • Hypotheses. Some theorems assume Doc.Valid, that the document is well formed in the sense the theorems define, or LowerRoom and ArgsRoom, that its lists fit the evaluator's bounded vectors (§07).
  • Try an instance. Where it helps, an instance runs a small model of the definitions in the page, so you can pick inputs and watch the property hold. It is a model computed here, not the contract.
  • Lean. The Lean names, linked to their lines at rule-core cbabe59 or Perch f0275f4.
  • Borders. Double for a theorem, single for a definition, dashed for the one argued proposition, which is not mechanized.

02From Rust to Lean

One Rust source takes two paths: one is translated into Lean, where the theorems are checked, and one is compiled into the account's Wasm, which is tested.

The evaluator is about 2,400 lines of dependency-free, no_std Rust that forbids unsafe code. It is written in a subset that Aeneas can translate: no traits, closures or iterator adaptors, and every loop a while over one slice.

Three tools connect that Rust to proofs. The Rust compiler lowers code to MIR, its mid-level intermediate representation. Charon reads the MIR that rustc nightly-2026-09-17 produces, and Aeneas [2] translates it into a pure functional program in Lean, a proof assistant whose small kernel checks every proof. The translation is a generated 3,653-line Lean file, and equivalence theorems relate it to the readable model, written by hand. rule-core's CI regenerates the translation and fails on any difference, so the Lean file the theorems are about is the one the pinned Rust produces.

The account does not ship that translation. It ships WebAssembly compiled by rustc 1.97.1, and nothing checks the Wasm against the translation. Figure 1 draws the two paths. Tests bridge them (§10); the proofs do not.

Ending authority. Four words recur in the theorems about recovery. A grant is invalidated when the account's generation passes the generation it was stamped with; it stays stored and refuses every nonempty batch. Removal (remove_grant, by the owner) deletes a grant's rules, tags and spending records. Collection (gc_grant, by anyone) deletes the storage of an invalidated grant and keeps the credential index. Archival is a lapse of an entry's time to live: the entry is unavailable until restored, not absent.

04The evaluator

Three theorems about the decision function: it matches the model on every input, accepts only what the rules allow, and accounts for every signer.

Theorem 1 is the bridge for the rest: the translated function succeeds on every input, so it neither panics nor loops, and its result denotes the model's. A property proved for the model therefore holds of the translation's results on denoted inputs. Most theorems below were also proved directly about the translation, and their Lean lines say which. Theorem 2 and Theorem 3 take the signer list as an input; authenticating it is the account's job (obligation O1, §10).

  1. Theorem 1 (Total equivalence of the evaluator)

    ∀x.∃y.authorizeT(x)=ok(y)∧⟦y⟧=authorize(⟦x⟧)\forall x.\ \exists y.\ \mathit{authorize}_{\mathrm{T}}(x) = \mathsf{ok}(y) \\ \qquad \land\ \llbracket y \rrbracket = \mathit{authorize}(\llbracket x \rrbracket)

    In words On every input, the Lean translation of the Rust decision function returns, without panicking or looping, exactly what the readable model returns.

    Precisely Here xx is the seven Rust inputs, and ok\mathsf{ok} is Aeneas's success, so neither a panic nor divergence. On every input the translated evaluator succeeds, never panicking or diverging, and its value denotes the model's result on the denoted inputs; this says nothing about allocation failure or compiled Wasm.

05Attenuation

Attenuation narrows a grant step by step. Two theorems say a derived grant allows no call its parent does not, and accepts no run from empty records that its parent would refuse. The account cannot install an attenuated grant at the pinned build.

Attenuation derives a narrower rule set from an existing one, for example to hand part of an app's authority to a helper. rule-core defines exactly 10 attenuation steps (Table 1); each returns a rule set that allows no call the original does not, and none changes a rule's target or generation. A move no step allows, such as raising a limit or shortening a period, is refused, not approximated.

  1. Theorem 4 (Attenuation narrows authority)

    Derives(R,R′)⟹R′⊑R\mathit{Derives}(R, R') \implies R' \sqsubseteq R

    In words A grant derived by attenuation steps allows no call its parent does not, under any signers; caps and expiry are outside this comparison.

    Precisely Successful attenuation by the ten attenuation steps yields a rule set narrower than its parent: under any signers, every call the child allows, the parent allows. Repeated derivation preserves this relationship. allows reads no cap or expiry, so the steps that add or tighten them narrow only over runs (Theorem 5); parent and child keep separate records, and neither theorem bounds what they spend together. The account has no entry point that installs an attenuated grant at the pinned build.

    Hypotheses Each derivation step is one of the ten attenuation steps and succeeds

    Try an instance

  2. Theorem 5 (Trace inclusion)

    attenuateAll(R,σ→)=R′∧Accepts(R′,∅,a→)⟹Accepts(R,∅,a→f),f=chainSource(σ→)\mathit{attenuateAll}(R, \vec\sigma) = R' \land \mathit{Accepts}(R', \varnothing, \vec a) \\ \qquad \implies \mathit{Accepts}(R, \varnothing, \vec a^{f}), \quad f = \mathit{chainSource}(\vec\sigma)

    In words Every run a derived grant accepts from empty records, its parent accepts too, with rule numbers renumbered.

    Precisely For a single successful derivation lineage, every accepted child history from empty records is accepted by the parent from empty records, with rule choices renumbered past dropped rules. Sibling histories are not covered. Here a→f\vec a^{f} renumbers each choice jj to f(j)f(j).

    Hypotheses Empty records; one derivation lineage

    Try an instance

Theorem 4 is about single calls: under any signers, whatever the child allows, the parent allows. allows reads no cap or expiry, so the steps that add or tighten those narrow only over runs. Theorem 5 is about histories: any run the child accepts from empty records, the parent accepts from its own empty records, with each rule choice renumbered past the rules a step dropped. It covers one derivation lineage, not two sibling grants spending together, and since parent and child keep separate records, neither theorem bounds what the two spend together. Both are proved for the model and the translation. They are results about rule-core: no Perch entry point installs an attenuated grant at f0275f4, and one is proposed (the Perch vision).

06Spending limits

A capped rule's charges stay within its limit in every window, and a delegation tree's spending stays within each node's allowance. The first runs in the account; the second is a model result.

The window bound is the evaluator's limit over time: a rule may carry a cap of λ per P ledgers, charged in the same decision that checks the call. The delegation-tree budget is rule-core's lifetime limit for a tree of grants, which the account does not use.

  1. Theorem 6 (Cap-window safety)

    spentj(R,∅,a→)=((tk,xk))k=1m⟹∀L.∑k:max⁡(0,L−Pj)<tk≤Lxk≤λj∧((∀a∈a→.ℓa≥1)⟹∀s.∑k:s≤tk<s+Pjxk≤λj)\mathit{spent}_j(R, \varnothing, \vec a) = ((t_k, x_k))_{k=1}^{m} \\ \quad \implies \forall L.\ \sum_{k:\ \max(0,\,L - P_j) < t_k \le L} x_k \;\le\; \lambda_j \\ \quad \land\ \bigl((\forall a \in \vec a.\ \ell_a \ge 1) \implies \\ \qquad \forall s.\ \sum_{k:\ s \le t_k < s + P_j} x_k \;\le\; \lambda_j\bigr)

    In words From an empty record, however the app times its payments, no window of P ledgers holds more than the limit in accepted charges.

    Precisely From empty records, in any run, counting its accepted authorizations, the charges made to a capped rule with a non-negative limit after L − P and through L sum to at most its limit, for every ledger L. For the model, every P consecutive ledgers starting at ledger 1 or later are bounded too, with no ledger assumption; the P ledgers from 0 are bounded when every authorization is at ledger 1 or later. The translated form bounds the model's spent on the denoted inputs, which Theorem 1 makes the translated run's charges.

The bound on chain

The evaluator keeps at most 1,000 entries in a record. On chain the binding limit is the size of one ledger entry: a spending record takes 172 bytes plus 72 per spend, so the network's 65,536-byte entry limit holds 907 spends per window. Further capped transfers through that rule fail until older spends leave the window, so a grantee can exhaust its own rule's window with small transfers. This is a refusal, never an excess: the theorem still holds.

07Documents, lowering and containment

A grant document becomes stored rules through lowering. Two theorems cover that step: what lowering refuses, and what the result allows once attenuated and accepted.

The account installs a grant by calling the document compiler, which validates the JSON and returns a model of the document, and then lowering that model with rule-core's lower_scoped under its own address AA, its excluded set XX and its current generation gg (Definition 6). In the account, XX holds its adopted recovery controller and the zero-knowledge adapter and pool of its recovery configuration; lowering refuses any rule whose target is AA or in XX.

Three hypotheses

  • Doc.Valid: every rule that requires all its signers names distinct signers, fewer than 2322^{32} of them, and no rule has a not-after ledger of 0. That Perch's compiler accepts only valid documents is recorded as unproven (unproven.perch-validation; obligation O5).
  • LowerRoom: the document's lists fit the evaluator's bounded vectors, so the translated lower has room to run.
  • ArgsRoom: the weaker condition that each rule's argument conditions fit, enough for the translated lower_scoped, refusals included.

08The account model and recovery

Recovery invalidation is proved in an abstract account with two events. The model has no Rust counterpart; the account's code is tested against it.

The account model (Definition 7) has a state of three parts, the account's address, its account document and its grant generation, and two events: apply a document, which keeps the generation, and complete a recovery, which installs the recovery target and advances the generation by one. Let HH be SHA-256, idA\mathit{id}_A the account's 32-byte contract ID, τ\tau the tag perch/account/auth-addr-v1, ids\mathit{ids} the selected rule IDs, and PP the host's signature payload: the hash of the XDR HashIdPreimage::SorobanAuthorization over the network ID, nonce, expiration ledger and invocation tree. The account computes

B=H(τ‖idA‖P)D=H(B‖XDR(ids))B = H(\tau\,\mathrm{‖}\,\mathit{id}_A\,\mathrm{‖}\,P) \\ D = H\bigl(B\,\mathrm{‖}\,\mathrm{XDR}(\mathit{ids})\bigr)

and an external signer signs DD. PP is the payload for a legacy Address credential; AddressV2 and delegated entries, from CAP-0071 [4], hash SorobanAuthorizationWithAddress, which adds the account. Lemma 1 (binding). Suppose the verifier named for an external signer correctly verifies an EUF-CMA-secure scheme and HH is collision resistant. An adversary given signatures on D(t1),…,D(tq)D(t_1), \dots, D(t_q), for tuples ti=(A,nid,nonce,exp,inv,ids)t_i = (A, \mathit{nid}, \mathit{nonce}, \mathit{exp}, \mathit{inv}, \mathit{ids}) of its choice, outputs a new tuple tt with a signature accepted on D(t)D(t) only with negligible probability.

Proof. The map from the tuple to DD composes injective encodings with HH. XDR encodes (nid,nonce,exp,inv)(\mathit{nid}, \mathit{nonce}, \mathit{exp}, \mathit{inv}) injectively, and its union discriminant separates the two credential forms; τ\tau is a constant, and idA\mathit{id}_A and PP have fixed lengths, so (A,P)↦τ‖idA‖P(A, P) \mapsto \tau\,\mathrm{‖}\,\mathit{id}_A\,\mathrm{‖}\,P is injective; BB has a fixed length and the XDR of ids\mathit{ids} is self-delimiting, so (B,ids)↦B‖XDR(ids)(B, \mathit{ids}) \mapsto B\,\mathrm{‖}\,\mathrm{XDR}(\mathit{ids}) is injective. If D(t)=D(ti)D(t) = D(t_i) for some ii, the injective encodings give a collision of HH; otherwise the output is a forgery. For WebAuthn, the signed message carries DD as the client-data challenge. ∎

The lemma covers signatures on DD values only; a key that also signs elsewhere, such as a Stellar account key, is covered only if no message it signs there can equal a DD value.

DD does not depend on the contents of the rules ids\mathit{ids} names, on the account's revision, on the other entries of the transaction or on its fee payer; none of these enters PP, BB or DD. Perch separates its hash domains with the tags perch/account/auth-addr-v1 (the account-bound payload BB, scheme addr_oz_v1), perch/rule (one rule's bytes), perch/recovery/statement, perch/recovery/config, perch/recovery/credential, perch/recovery/replacements (recovery statements, configurations, credentials and replacement sets), and, as Poseidon2 constants, perch/recovery/zk/v2/leaf, perch/recovery/zk/v2/bind, perch/recovery/zk/v2/nullifier, perch/recovery/zk/v2/auth. The proofs rest on a kernel, a translation toolchain and a specification written by hand. The deployed account rests on more.

What the proofs trust

  • Charon 7b462d9, Aeneas ab34bd2, and Aeneas's Lean library, which models Rust's primitives.
  • The MIR that rustc nightly-2026-09-17 produces.
  • The specification: the denotation functions (Definition 9), and the document meaning Doc.allows, written from Perch's earlier account at dff2a73.
  • The host models, tested against soroban-env-host 29.0.1 and 30.0.0.

The deployed account also relies on rustc 1.97.1 and its WebAssembly back end, which build the contract; the document compiler, which turns grant JSON into the model the account lowers; the tested account shell, verifiers and recovery controller; and soroban-env-host (Figure 1).

Cryptographic assumptions

The binding lemma assumes an EUF-CMA-secure scheme and a collision-resistant SHA-256, and Theorem 13 gives hash identity only up to SHA-256 collisions. Ed25519 [6] signatures are checked with strict verification. P-256 signatures are ECDSA with low S enforced; the WebAuthn verifier [7] checks neither the relying-party ID nor the origin. ML-DSA-65 is pure FIPS 204 [8] with a fixed context string, the key being the hash of the public key. The compiler refuses a key not in its verifier's canonical form, so a threshold, which counts distinct identities, cannot count one key twice. The deployed Ed25519 and WebAuthn verifiers trap on a bad signature (Error(Crypto, InvalidInput) for Ed25519) rather than return false; the built ML-DSA-65 verifier returns false for a well-formed failing signature. A grant may name a verifier by address alone; each such verifier may supply at most one signer per rule. Ed25519, P-256 and BN254 are not post-quantum, and administrative signers, guardians and the zero-knowledge factor can each change the account's rules, so an ML-DSA-65 signer resists a quantum adversary only if every such path does. A contract ID commits to its deployer and salt, not its code, so calling fixed infrastructure code assumes that the registry deploys each pinned Wasm hash at the salt derived from it and that those contracts cannot replace their code.

The zero-knowledge recovery factor proves knowledge of a secret enrolled as a Poseidon2 commitment in a depth-32 pool, with an UltraHonk proof with KZG commitments over BN254 against a fixed setup point and Fiat–Shamir with Keccak; Perch's docs/zk/ does not name the setup ceremony. The commitment is public, so the secret must be a uniform field element with at least 128 bits of entropy. Perch's zero-knowledge verifier has not been audited. None of these assumptions enters a Lean theorem; they bear on the account, and on Lemma 1 (§10).

They are hypotheses of the model (bounded room, the empty batch, no creation vocabulary, ledgers from 1) and the trusted items above. Several of the unproven ones are the obligations of Table 2 seen from rule-core's side; five record correspondences between rule-core's definitions and OpenZeppelin's account and spending_limit code, read from source and neither proven nor tested against it.

12What is not proved

The proofs cover the decision function's translation, not the compiled contract, the code around it, the host, or what happens outside an authorization.

The proofs and the binary

The theorems are about the translation of the MIR that rustc nightly-2026-09-17 produces. rule-core's CI also builds the evaluator with rustc 1.99.0, Perch builds its contracts with rustc 1.97.1, and nothing checks the Wasm against the translation (Figure 1). Release builds keep overflow checks and abort on panic, and allocation failure and stack exhaustion, which the functional model omits, also trap, so each fails the transaction rather than authorizing. The specification is itself trusted: the denotation functions; the document meaning Doc.allows, written from Perch's earlier account (dff2a73, on OpenZeppelin's library at 33726766) and not re-derived from the pinned gate; and the Soroban host models.

The shell and the host

Tested, not proved: the JSON parser and compiler, stored-value decoding, rule-ID resolution, context conversion, assembly of the excluded set, spending-record persistence, the credential index, the generation update, the composition of evaluation with authentication, and the recovery controller's state machine. The integration tests run the account's real __check_auth under enforcing authorization, but as natively registered contracts; the Wasm, with passkeys and real proofs, runs in Perch's release_stack.rs flows and on testnet. The host models are tested against selected traces, not proved equivalent to soroban-env-host, and leave out TTL, archival, fees, footprints and validation before the host runs; soroban-sim, the host the Perch papers' simulations use, is another tested host integration. No single theorem covers the whole pinned gate, including mixed administrative and grant batches, so Proposition 1 is argued, not proved.

Proofs that would close gaps (proposed)

  • A Lean lemma for obligation O2, so that selection and renumbering of rules carry the evaluator's theorems to the account by proof rather than by argument and tests.
  • Checking the compiled evaluator directly: Komet [9], a formal-verification tool for Soroban Wasm, run over rule_eval's Wasm.
  • A host-model statement for authorization by invoker, which Theorem 11 leaves out by construction; the owner's execute is its example.
  • A proof that Perch's compiler emits only valid documents (O5), and a theorem connecting the canonical encoding to rule-core's document type.

All four are proposed. No external audit of Perch has been completed.

13Related work

Other verified authorization engines link their model to their code by testing; here the link from the Rust to the model is a proof, and the step to the Wasm is trusted.

Cedar [10] specifies its authorization semantics in Lean and links that model to its Rust implementation by differential random testing [11]. Here the link is a proof: Charon [12] and Aeneas [2] translate the Rust evaluator into Lean [13], and Theorem 1 proves the translation equal to the model on every input. The step from that Rust to the shipped Wasm stays trusted; Wasm-level tools for Soroban, Sunbeam [14] and Komet [9], could check it.

14Conclusion

Thirteen kernel-checked statements cover Perch's decision function and lowering, through their Aeneas translation, and an account model and a host model.

Proposition 1, argued rather than mechanized, carries Theorem 1, Theorem 8, Theorem 9 and Theorem 10 to the account under eight obligations, one of them (O5) unproven. The compiled Wasm and the hand-written specification stay trusted, and no external audit has been completed.

AReproducing the proofs

The proofs reproduce from rule-core's repository at the pinned commit, with pinned tools.

rule-core cbabe594ae2df408991e825e56ddd618ea29541b builds its proofs with Charon 7b462d9, Aeneas ab34bd2 and Lean v4.35.0, over the MIR of rustc nightly-2026-09-17. Two commands do the work: tools/extract.sh --check regenerates the translation and fails if it differs from the committed file, and lake build in formal/ checks every proof; rule-core's README gives the prerequisites and the full commands. The claims ledger and the axiom pins run in the same CI.

Perch's canonical-encoding package (formal/PerchFormal/ at Perch f0275f4) uses Lean v4.33.0 and builds separately. Every Lean name on a card links to its line at one of these two commits. Checking the exported declarations in a browser is proposed in the Perch vision.
