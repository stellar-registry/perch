# @stellar-registry/perch-contracts

TypeScript clients for the perch stack contracts, generated by `stellar
contract bindings typescript`, plus deployment manifests. Modules generated
from unreleased builds are explicitly marked undeployed (see below).

```sh
npm install @stellar-registry/perch-contracts
```

| Module | Contract |
| --- | --- |
| `account` | `perch-account`: `apply_doc`, `apply_grant`, `execute`, `applied_doc`, `infra`, upgrades, `cancel_recovery`, the consumer views `revision`, `configuration`, `document`, `capabilities`, and the grant views |
| `factory` | `perch-account-factory`: `create`, `create_passkey`, `address_of`, `passkey_address` |
| `recovery` | `perch-recovery`: attempts, guardian and ZK evidence, change approvals, statements |
| `pool` | `perch-zk-pool`: trees, leaves, roots, enrollments |
| `adapter` | `perch-zk-adapter`: `verify`, `circuit_id`, `tree_depth` |
| `webauthnVerifier` | `perch-webauthn-verifier` |
| `docCompiler` | `perch-doc-compiler`: `compile_doc`, `derive_target`, `limits`, `grant_limits`, `capabilities` |
| `legacyAccount`, `legacyDocCompiler` | the deployed `perch-account` and `perch-doc-compiler` specs (snapshot 1; see below) |

```ts
import { factory, addressOf, testnet } from '@stellar-registry/perch-contracts';

const f = new factory.Client({
  contractId: addressOf(testnet, 'perch-account-factory'),
  networkPassphrase: testnet.network_passphrase,
  rpcUrl: testnet.rpc_url,
  publicKey, // the fee payer
  signTransaction,
});
const tx = await f.create_passkey({ salt, key_data: passkeyPublicKey });
```

Each module exports `WASM_SHA256`, the hash of the wasm it was generated
from; `npm test` fails if it, or `testnet`, drifts from
`deployments/testnet.json`. Regenerate with `scripts/bindings-contracts.sh`
after a deployment. A module regenerated from a stack built from source
(`scripts/bindings-contracts.sh --undeployed <stack> <module>...`), for a
contract change not deployed yet, exports `DEPLOYED = false` and is exempt
from that check until the next deployment regenerates it.
`PERCH_LIVE=1 npm test` also calls the deployed contracts through the
bindings.

A recovery completion (`apply_doc` through the zero-signer recovery rule)
must be simulated with its recovery-rule authorization entry already in the
transaction. Recording-mode simulation never runs `__check_auth`, so the
controller's `rcv_complete` never marks the call as the completion and
`rcv_sync` refuses it as a change during the authorized window. See
[`docs/deploy/README.md`](../../docs/deploy/README.md#simulating-a-recovery-completion).

The `account` and `docCompiler` bindings, from the build that stores rules
compactly (snapshot 3), are marked undeployed. `legacyAccount` /
`legacyDocCompiler` (also the `/legacy-account` and `/legacy-doc-compiler`
package exports) retain the recorded deployed spec. Read `capabilities()`
before `configuration()`: snapshot 1 uses the legacy account spec, and
snapshots 2 and 3 the current one, whose `configuration()` is the same in
both. The stored-rule views (`rule_set`, `grant_rule_set`, with
`rule_signers` and `grant_signers`) decode only snapshot 3's tuples. Select
a compiler binding matching that account's pinned compiler, and refuse
unknown snapshot versions.

The Stellar SDK decodes struct fields by position. The current spec cannot
safely decode old rule maps, and the account itself no longer reads them.
`perch-js`'s `readSnapshot` supports every snapshot's `configuration()`
through a matching `AccountReader`; it cannot repair a result already
misdecoded by the SDK.
