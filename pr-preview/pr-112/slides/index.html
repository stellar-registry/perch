02 · Problem

Restricting an operational key to one call

Operational keys (wallet session keys, treasury payout keys, agent tool keys, CI keys that publish wasm) each need authority over a narrow set of calls. On Soroban, restricting a key to specific functions and arguments requires a contract written and audited for that purpose. The example used throughout this deck is a CI key in GitHub Actions that publishes releases to the registry. The account must enforce, on-chain:

This key may call publish on the registry contract, as the account — and nothing else.

Without perch this needs a custom policy contract. With perch it is a policy document (JSON), compiled into OZ context rules and an interpreter program.

04 · Soroban authorization

Contract accounts authorize in __check_auth

A contract account has no built-in permission model. When a call requires the account's authorization, the host (the Soroban runtime) calls the account's __check_auth(signature_payload, signatures, auth_contexts). Each context names the contract, function, and arguments being authorized; the function returns Ok(()) or an error.

Anything __check_auth does not reject is authorized, so a restriction such as "publish only" must be implemented in code the account runs.

05 · Without perch · option 1

A hand-written __check_auth

pub fn __check_auth(e: Env, payload: Hash<32>, sigs: MySigs, contexts: Vec<Context>) -> Result<(), Error> {
    verify_ed25519(&e, &payload, &sigs)?;                  // signature verification, implemented by the account
    for ctx in contexts.iter() {
        match ctx {
            Context::Contract(c) => {
                if c.contract != registry()            { return Err(Error::NotAllowed); }
                if c.fn_name  != symbol("publish")    { return Err(Error::NotAllowed); }
                // arguments, expiry, and other signers: not checked here
            }
            _ => return Err(Error::NotAllowed),          // deploy contexts and anything else: refused
        }
    }
    Ok(())
}
  • Each account implements its own authorization code, which every call made in its name depends on.
  • An unchecked argument or a signature-verification bug authorizes calls the account should refuse.
  • Each account needs its own audit; reviewing one does not cover another.

06 · Without perch · option 2: OZ stellar-accounts

OZ context rules: add_context_rule

OpenZeppelin's stellar-accounts library replaces hand-written checks with context rules in the account's storage: a scope, signers, optional policy contracts, and an expiry. This call installs the CI key's rule:

add_context_rule(
    &env,
    &ContextRuleType::CallContract(registry),  // scope
    &String::from_str(&env, "ci-publish"),    // name
    Some(55_000_000),                          // expiry
    &vec![&env, Signer::Delegated(robot)],    // signers
    &Map::new(&env),                            // policies
)
  • scopeCallContract(address): calls to one contract. The other ContextRuleType variants cover deploying a given wasm hash, or any context (Default).
  • expiryOptional ledger sequence after which the rule no longer matches.
  • signersSigners that must authenticate, at most 15. Here one: Signer::Delegated(robot), the CI key's G address.
  • policiesPolicy contracts whose enforce the account calls, at most 5. Empty here.
  • administrationadd_context_rule, add_signer, add_policy, … are entry points on the account, authorized by its own rules.

07 · Without perch · OZ signer types

Signer: Delegated and External

pub enum Signer {
    /// A delegated signer that uses built-in signature verification.
    Delegated(Address),
    /// An external signer with custom verification logic.
    /// Contains the verifier contract address and the public key data.
    External(Address, Bytes),
}

stellar-accounts, smart_account/storage.rs (verbatim)

Delegated(address)

Another address authenticates: for the CI key, its G address. With CAP-0071 (protocol 27) the host verifies that address's signature inside the smart account's own authorization entry (SorobanCredentials::AddressWithDelegates), not in a separate entry.

External(verifier, key)

Key bytes plus a verifier contract implementing verify(signature_payload, key_data, sig_data) -> bool. A new signature scheme is a new verifier contract; perch deploys ed25519 and WebAuthn (secp256r1) verifiers.

08 · Without perch · a minimal OZ account

A minimal OZ smart account (perch-account)

#[contract]
pub struct PerchAccount;

#[contractimpl]
impl PerchAccount {
    /// Deploy-time rule 0: the admin signers may manage this account — and nothing else.
    pub fn __constructor(e: &Env, admin_signers: Vec<Signer>) {
        smart_account::add_context_rule(e,
            &ContextRuleType::CallContract(e.current_contract_address()),

}

impl CustomAccountInterface for PerchAccount {
    type Error = SmartAccountError;

    fn __check_auth(e: Env, signature_payload: Hash<32>, signatures: AuthPayload,
                    auth_contexts: Vec<Context>) -> Result<(), Self::Error> {
        smart_account::do_check_auth(&e, &signature_payload, &signatures, &auth_contexts)
    }
}

09 · Without perch · OZ evaluation

do_check_auth in four steps

stellar_accounts::smart_account::do_check_auth, called from the account's __check_auth:

  1. Select

    AuthPayload.context_rule_ids names one rule per context. The ids are hashed into the signed digest, sha256(signature_payload ‖ xdr(ids)), so a relayer cannot substitute another rule.

  2. Match

    Load the rule; check it has not expired and that its scope covers the context.

  3. Authenticate

    Every signer provided: Delegated → the host verifies the signature. External → the verifier contract verifies the bytes.

  4. Enforce

    Call enforce(…) on every policy attached to the rule. Any failure rejects the transaction.

10 · Without perch · library behaviors

Four stellar-accounts behaviors perch constrains

Each is documented library behavior. The line under each card is how perch handles it.

ContextRuleType::Default matches any context

The library documents Default as able to "authorize any context". A rule with this scope authorizes every call the account can make.

the document format has no "anything" scope. A rule names the account itself or one contract; anything else fails to parse.

With a policy attached, signer checks move to the policy

With no policies, every rule signer must authenticate. With policies attached, the library defers signer checks to them, so a policy that skips them drops the signer requirement.

the compiler injects a minimum-signer check into every program, and the interpreter denies outright when no signer authenticated.

Overlapping rules are the caller's to manage

Several rules can cover one contract, and the signer selects the rule id. The library docs: "It is the caller's responsibility to avoid creating redundant rules." A rule that is not removed stays active.

one document names every rule. Verification reads the account back and compares — a leftover is a detected mismatch, not a mystery.

The account accepts the attached policy's result

The account calls the attached contract's enforce and accepts its result. Nothing requires a policy to refuse by default.

the interpreter is the one policy contract, and it denies by default: no program installed for a rule → deny.

11 · Without perch · contract-level scope

CallContract scope covers every function

A rule scoped CallContract(registry) authorizes:

Required

  • ▸publish

Authorized by CallContract(registry)

  • ▸publish
  • ▸set_manager — reassigns management of the registry
  • ▸upgrade, and every other method it has

Restricting the function or its arguments needs a policy contract: custom Rust, written, audited, and deployed for each kind of constraint. Perch provides that policy as one shared interpreter contract plus a per-rule program compiled from a reviewed document.

14 · Perch · canonical form

doc_hash: SHA-256 of the canonical form

CANONICAL.md defines the canonical byte form, independent of any JSON library: sorted keys, no whitespace, one escaping rule. Rust (perch-ir) and TypeScript (perch-js) produce identical bytes, pinned by shared vectors in testdata/; a one-byte difference fails CI.

16 · Perch · apply_doc

apply_doc: the account's only authorization write path

A perch account does not export OZ's mutation entry points (add_signer, remove_signer, add_policy, …). Parsing and compiling run in the shared, stateless perch-doc-compiler contract; the account stores its rules and applied document and changes them only through apply_doc:

pub trait PerchSmartAccount: CustomAccountInterface + SmartAccount {
    /// Apply a policy document — the ONLY way authorization changes.
    fn apply_doc(e: &Env, doc_json: Bytes, approval_valid_until: u32)
        -> Result<BytesN<32>, PerchAccountError> {
        e.current_contract_address().require_auth();   // the admin rule
        let compiler = infra::perch_doc_compiler::address(e);  // pinned at build
        let compiled = DocCompilerClient::new(e, &compiler)
            .try_compile_doc(&doc_json)??;      // stateless, shared
        if !admin_survives(&compiled.rules) { return Err(AdminLockout); }
        // …refuse revoked credentials; rcv_sync classifies…
        // …replace every rule, atomically; store the bytes…
    }
    fn applied_doc(e: &Env) -> Option<Bytes> { … }
    fn applied_doc_hash(e: &Env) -> Option<BytesN<32>> { … }
}
  • one invocationThe reviewed JSON replaces the whole rule set in one invocation, with no intermediate state. doc_hash is over the canonical form, so formatting does not change it.
  • anti-brickadmin_survives: a document with no working self-admin rule returns AdminLockout before any rule changes.
  • pinned infraThe compiler and interpreter are not arguments: their addresses are baked in at build time and reported by infra(). Using a newer compiler requires a new account build.
  • shippedA 46,701-byte account wasm with 22 exports (slide 31); the compiler, 104,767 bytes, exports compile_doc and derive_target.
# perch-deploy signs the admin's smart-account approval, which the stock CLI cannot yet:
perch-deploy apply --account C…ACCT --doc policy.json
# read the applied hash with the stock CLI (a simulation; no keys):
stellar contract invoke --id C…ACCT -- applied_doc_hash

applied_doc_hash identifies the account's authorization state; applied_doc returns the full canonical document.

17 · Perch · a publish transaction

A CI publish, step by step

  1. The CI key signs

    stellar contract invoke --id C…REG --source robot -- publish --wasm … --author C…ACCT

    The GitHub Actions job holds only the CI key's secret; with CAP-0071 the host verifies its signature inside the account's authorization entry. perch-deploy publish builds that entry selecting rule 1, which the stock CLI cannot do yet.

  2. OZ matches the rule

    __check_auth → do_check_auth loads rule ci-publish and authenticates the CI key as its Delegated signer.

  3. OZ calls the interpreter's enforce

    The rule's attached policy is the shared interpreter, which loads the program stored for (account, rule id).

  4. The program checks the call

    Checks fn_name ∈ {publish, publish_hash}, argument 1 = the account, and ledger ≤ 55,000,000. Any failure rejects the transaction.

18 · Perch · audit surface

Audit surface with and without perch

Without perch

One policy contract per kind of constraint, per team, each audited separately.

n teams × m constraints

With perch

Shared contracts with no admin or upgrade path, audited once: the interpreter (evaluation — machine-checked core, 16,989 bytes) and the doc compiler (parsing + compiling — stateless, 104,767 bytes); for recovery, one controller, one pool, and one adapter (slides 30–31). None has an admin or an upgrade path. The account is a 46,701-byte wasm with zero policy logic of its own.

After that audit, a new policy is a document to review rather than a contract to audit.

19 · Verifiers

perch-ed25519-verifier

An External signer names a verifier contract: stateless, deployed once per network, shared by every account. A signature scheme is added by implementing the Verifier trait. The ed25519 verifier (1,413 bytes deployed):

#[contract]
pub struct PerchEd25519Verifier;

#[contractimpl]
impl Verifier for PerchEd25519Verifier {
    type KeyData = BytesN<32>;  // an ed25519 public key
    type SigData = BytesN<64>;  // an ed25519 signature

    fn verify(e: &Env, signature_payload: Bytes,
              key_data: BytesN<32>, sig_data: BytesN<64>) -> bool {
        ed25519::verify(e, &signature_payload, &key_data, &sig_data)
    }
}

20 · Verifiers · post-quantum (sketch)

An ML-DSA verifier (not implemented)

ML-DSA (FIPS 204) is a post-quantum signature standard; ed25519 is not. An ML-DSA public key is larger than a signer's key field, so the verifier stores a hash of it.

#[contractimpl]
impl Verifier for PerchMlDsaVerifier {
    type KeyData = BytesN<32>;  // NOT the key — sha256(public key)
    type SigData = Bytes;       // full public key + signature

    fn verify(e: &Env, signature_payload: Bytes,
              key_data: BytesN<32>, sig_data: Bytes) -> bool {
        let (public_key, signature) = split(e, &sig_data);
        e.crypto().sha256(&public_key).to_bytes() == key_data
            && ml_dsa::verify(e, &signature_payload, &public_key, &signature)
    }
}
  • key_data: a commitmentAn ML-DSA-44 public key is 1,312 bytes; a document's signer key is at most 256 bytes (perch-ir). key_data is the 32-byte sha256 of the public key; perch-ir's key-size comment names "commitment-style keys".
  • sig_dataCarries the public key and the signature. verify checks the hash against key_data, then the signature.
  • statusThe same Verifier trait as ed25519. Not implemented; on the roadmap (slide 35).

24 · Recovery · overview

Recovery: the document's recovery member

A document's optional recovery member enrolls the account at a recovery controller: a profile, a mode, timing in ledgers, and the signer ids a recovery may replace. docs/recovery/spec.md (decisions D1–D16) specifies the states, the transitions, and the authorization each one needs. Evidence types:

  • Guardians — any Stellar addresses, G… or C…, and a quorum of them.
  • A ZK credential — a proof of knowing a secret whose commitment the account enrolled in a membership pool, without revealing which leaf.
  • Both — a quorum and a proof.

A recovery installs a target document the controller derives on-chain from the account's current state (slide 27); no caller supplies a target hash.

27 · Recovery · permitted changes

Recovery targets: derive_target and revocation

lost key

The applied document, with replacements

The source is a snapshot of the account's applied document; derive_target replaces exactly the declared signer slots. A replacement keeps the slot's kind and verifier. If the source changes before the attempt is authorized, the attempt can never promote — start a fresh one.

compromise

The enrolled baseline, restored

The source is a baseline whose hash the recovery member enrolled and anyone may publish: its signers and rules, the current recovery member, and the replacements. Signers and rules added after the baseline are not in the target.

  • Revocation. Every replaced credential, and every credential a compromise removes, joins the account's permanent revoked set — checked on every apply_doc, on every path.
  • Completion versus reconfiguration. A completion is not a reconfiguration. It is recognized by the attempt it consumes in the same invocation. Configuration identity is the recovery member's canonical text, so rotating a signer's key never counts as reconfiguring recovery.

28 · Recovery · the freeze

Protected freeze: a FreezeGate in account storage

Why a mirror: Soroban refuses to re-enter a contract already on the call stack. A perch account can be a guardian at the controller it uses itself, and then its __check_auth runs while that controller is mid-call. A read of the controller from __check_auth would then fail with Error(Context, InvalidAction), so the controller sets the gate, through the account's invoker-only rcv_gate, and no hook ever calls back into the account.

29 · Recovery · invoker-only hooks

Invoker-only hooks and the compile-time scope rule

The account never authorizes

  • ▸install · uninstall · enforce
  • ▸rcv_sync · rcv_cancel · rcv_upgrade
  • ▸rcv_insert · rcv_gate

On any contract, through __check_auth or execute. The hooks are reachable only from the account's own flows, which closes direct configuration writes (#90).

The compiler refuses (narrowed rule)

  • ▸a rule scoped to the document's own ZK adapter
  • ▸a rule scoped to the document's own pool
  • ▸a rule scoped to its own controller — allowed

A perch account that guards others at its own controller must sign submit_guardian and approve_change there. The reserved-name guard, not the scope rule, protects the controller's hooks.

30 · Recovery · ZK

Membership pool and ZK adapter: reproducible builds

perch-zk-pool

Depth-32 trees with rollover

No constructor, admin, or upgrade. An account inserts its own leaf through the invoker-only rcv_insert; the pool binds it to that account and enrollment id.

232 leaves per tree. The insertion that fills a tree seals it; the next opens a new one. Every root a tree has ever had stays acceptable.

perch-zk-adapter

NethermindEth's UltraHonk verifier (internally reviewed and audited by OpenZeppelin), vendored unmodified at c2160987, with the circuit's verification key compiled in. circuit_id = sha256 of that key.

It checks the circuit, field canonicality, the root against the enrolled pool, and the 14,592-byte proof.

circuits/manifest.json

Pinned artifacts

31 · Recovery · controller and account

perch-recovery and the account's entry points

perch-recovery · 63,162 bytes

The controller

Constructorless and immutable; per-account state only. Attempts, evidence, cancellation, completion. A per-account epoch, bumped on every configuration change, invalidates every earlier attempt and approval. Nullifiers are spent only by a completion, recorded per account, never released.

perch-account · 46,701 bytes

The account's capabilities

execute(target, fn, args) — calls target as the account; reserved names refused. applied_doc() — the full canonical document. infra() — what it resolves.

schedule_upgrade → 120,960 ledgers (seven days) → execute_upgrade. Under Protected the condition approves the exact wasm hash and request id. Refused during an authorized attempt; any epoch change makes a queued request stale; a completed recovery drops it.

perch-account-factory (4,717 bytes) deploys the account wasm it was built against. The deploy salt is sha256(salt ‖ xdr(admin_signers)), so a predicted address can only be created with the signers it was computed for. create_passkey names the pinned WebAuthn verifier.

32 · Release · pin order

Build order: tier 0, then the account, then the factory

  1. Tier 0 — pins nothing

    Compiler, interpreter, spending limit, both verifiers, pool, adapter, controller. Each deployed content-addressed: address = deployer(registry, sha256(wasm)), known before deployment.

  2. Tier 1 — the account

    Built with tier 0's exact bytes and the registry id staged as its pins.

  3. Tier 2 — the factory

    Built with the account wasm and the WebAuthn verifier as its pins.

  4. The manifest

    deployments/testnet.json records every hash, address, and pin. fetch-infra-wasm.sh refuses any byte whose sha256 or content address doesn't match it; verify-deployment.sh checks the chain — including what the factory and each account actually resolve. Never a name lookup alone.

Previously scripts/fetch-infra-wasm.sh resolved the compiler by name through a deploy nothing updated, so builds pinned the pre-cap v0.1.0 compiler (#95). A rebuild from the deployment commit now reproduces every recorded hash.

Ownership: Perch and Nido

perch

Contracts, packages, tooling

The shared smart account — execution, full document reads, policy management, controlled upgrades. The WebAuthn verifier and the account factory. One recovery controller and statement specification. The circuit, verifier, adapter, pool, proof SDK, and reproducible artifacts. Indexer and relay software, bindings, integration tests, deployment tooling, audit-facing documentation.

nido

Wallet and hosted services

Wallet UI, account naming, product defaults, and the passkey and recovery experience. Operating the hosted services. Integrating the published Perch contracts and packages — @stellar-registry/perch-contracts, perch-zk and its indexer, perch-relay — from the manifest.

35 · Roadmap

Roadmap

  1. Nido on the shared stack now

    Fresh wallet accounts from the factory; onboarding and every recovery combination through apply_doc.

  2. Client proving budgets

    Proving on the reference phone and laptop is unmeasured; native proving and every on-chain row are measured.

  3. Canonical publication

    Tier 0 into the release pipeline's allow-list, then the account and the factory in pin order.

  4. Stock-CLI signing

    Teach the stellar CLI to sign smart-account approvals, so the perch-deploy shim disappears.

  5. Audit, then mainnet

    Audit of the implementation with its specification, threat model, and measured costs; then a mainnet deployment.

  6. CAP-0071 upstream, then ML-DSA

    The delegated-signer patch merged into upstream stellar-accounts; an ML-DSA verifier.
